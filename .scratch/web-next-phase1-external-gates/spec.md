# Phase 1 外部门验收（NEXT-01、NEXT-02、NEXT-07 残留）

Status: ready-for-human

## Problem Statement

Phase 1 的本地候选矩阵已全绿并获得用户确认（2026-10-07），但整票仍未关门：真实 Google OAuth 与 SMTP 的注册、登录与找回从未在真实凭据下验收；外部渠道的真实死信处理没有验证；界面缺少独立视觉复审；真实付费运行时也没有签收。这些门都依赖外部服务、真实凭据或付费授权，不能在沙箱内代跑。

作为部署者，我想在真实凭据与外部服务下逐项验收，这样 NEXT-01、NEXT-02、NEXT-07 才能从"本地全绿"变为整票完成，Phase 7 的 go/no-go 才有依据。

## Solution

四项 `ready-for-human` 验收切片，各自明确前置条件、执行步骤、证据要求与失败处理：真实 OAuth/SMTP 端到端、外部渠道死信与投递、独立视觉复审、真实付费运行时签收。

## User Stories

1. 作为部署者，我想在真实 Google OAuth 凭据下完成注册、登录与找回。
2. 作为部署者，我想在真实 SMTP 下收到验证与找回邮件并完成链接流程。
3. 作为部署者，我想确认半配置状态下启动失败并给出明确原因。
4. 作为部署者，我想在没有邮件投递时看到明确不可用说明（503 与界面说明）。
5. 作为部署者，我想在真实外部渠道上产生一次投递失败并处理死信。
6. 作为部署者，我想验证死信重试幂等，不重复外发。
7. 作为部署者，我想验证撤权后立即停止投递。
8. 作为审查者，我想对界面做一次独立视觉复审并给出问题清单。
9. 作为审查者，我想视觉复审覆盖桌面与手机视口。
10. 作为审查者，我想复审结论区分阻塞问题与非阻塞建议。
11. 作为部署者，我想在真实付费运行时上完成一次完整会话与交接流程。
12. 作为部署者，我想记录真实运行时的成本与配额影响。
13. 作为部署者，我想失败时明确记录为未完成，不勾选整票。
14. 作为维护者，我想四项验收的证据与结论入库，原始证据留 `.scratch/`。
15. 作为维护者，我想这四项不阻塞其他阶段，但阻塞 Phase 7 的 go/no-go。
16. 作为部署者，我想每项验收有可重复的执行步骤。
17. 作为维护者，我想不因外部依赖缺失而降低验收标准。
18. 作为部署者，我想知道每项的前置条件（凭据、域名、付费授权、复审人）。
19. 作为维护者，我想验收期间不改动产品代码，除非发现阻塞缺陷并登记。
20. 作为用户，我想真实邮件与 OAuth 流程的体验被验证过，而不只是本地桩。

## Implementation Decisions

- 四项各自独立，均为 `ready-for-human`；Agent 不代跑，只准备步骤、脚本与证据模板。
- 每项验收必须记录前置条件、执行时间、真实服务与凭据来源（不落明文凭据）、输出与结论。
- 邮件链接只由 `WEMUX_PUBLIC_URL` 拼接，验收需覆盖该约束。
- 死信验收使用真实渠道，产生真实失败并记录重试与撤权行为。
- 视觉复审由独立人员或独立会话执行，产出问题清单与处置结论。
- 付费运行时验收记录模型、成本与配额，不扩大到日常开发流程。
- 未通过项如实标注为未完成并登记缺口；不得以本地桩结果代替。

## Testing Decisions

- 复用现有 seam：注册/登录/找回接口与邮件出件箱、渠道投递与死信处理、web-next 界面、Runtime 会话启动路径。
- 只测外部行为：真实邮件可达、OAuth 回调完成、死信可诊断与幂等重试、撤权停止投递、真实运行时完成流程。
- Prior art：Phase 1 本地候选矩阵、`docs/acceptance/` 既有验收摘要、`apps/e2e` 脚本。
- 证据要求：截图、日志、断言输出与成本记录；脱敏后入库。

## Out of Scope

- 产品功能开发。
- 沙箱内可完成的部分（已完成）。
- Phase 7 的切根动作。

## Further Notes

- 前置：无（四项可随时开始，但都需要外部条件）。
- 这四项是 Phase 7 go/no-go 的输入；未过项不得进入切根。
