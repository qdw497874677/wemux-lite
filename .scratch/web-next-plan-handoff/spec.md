# 项目管理 Agent、按需计划批准与执行交接（NEXT-06、NEXT-08）

Status: ready-for-agent

## Problem Statement

任务驱动建立在手工会话之上，目的是组织多个任务和会话完成项目。现有规格将项目管理能力缩成“先批准计划再交接”，遗漏按授权创建和管理任务、安排执行、发现阻塞、读取成果并持续跟进的完整路径。

作为 Team 成员，我想手工或委托项目管理 Agent 操作同一套项目任务，组织执行并跟踪结果。要求先审计划时才进入 revision 批准流程；范围已获授权时不增加重复确认。讨论会话不直接实施，代码修改等仍交给普通 Task 下的执行会话。

## Solution

1. **项目管理与按需批准**：用户与获授权 Agent 共用项目查询、任务创建/更新、依赖与阻塞、执行安排、会话/成果查询和显式提交能力。计划保存为不可变 revision；仅用户或策略要求审批时，批准具体 revision，新 revision 不继承旧批准。
2. **交接**：协调会话内提供交接操作，原子、幂等地在目标 Project 创建普通 Task，携带计划、验收标准与来源协调 Task/Session 引用；创建与实际启动在领域上分离；创建为 backlog 仅暂存，获权创建为 todo 或迁移至 todo 即由状态驱动派发，无独立入队开关或重复确认。
3. **执行闭环**：现有有效 Runtime 以各自合适入口完成同一"项目查询 → 交接 → 执行 → 报告"流程，结果以引用形式回到协调上下文；复用现有审查合同，Run 成功不自动 done。
4. **签收**：同候选测试与 e2e 全绿，真实执行证据与 Runtime 差异明示。

## User Stories

1. 作为 Team 成员，我想把协调会话里形成的计划保存为 revision，这样定稿可追溯。
2. 作为 Team 成员，我想对某个具体 revision 批准，这样批准对象明确、不含糊。
3. 作为 Team 成员，我想修订计划后旧批准自动失效，这样批准不会被误用到新内容。
4. 作为 Team 成员，我想看到每个 revision 的批准状态与批准人。
5. 作为 Team 成员，我想把已获授权的工作交接到目标 Project 的普通 Task；若要求先审计划，则必须有对应 revision 批准。
6. 作为 Team 成员，我想交接一次只创建一个 Task，重复请求不重复创建。
7. 作为 Team 成员，我想交接出的 Task 携带计划、验收标准与来源引用，这样执行者不用猜。
8. 作为 Team 成员，我想将暂不执行的交接任务保存为 backlog，检查好后再改为 todo。
9. 作为 Team 成员，我想自己或获授权 Agent 将任务创建为 todo 或推进至 todo，平台便按机器范围和容量安排执行，不再要求独立入队操作。
10. 作为 Team 成员，我想执行完成后在协调会话里看到结果与产物引用，这样讨论能继续。
11. 作为 Team 成员，我想执行 Agent 能查询项目、交接、执行、报告，这样闭环不靠人工搬运。
12. 作为 Team 成员，我想每个有效 Runtime 用各自合适入口完成同一流程，这样平台不被单一 Runtime 绑定。
13. 作为 Team 成员，我想 Runtime 之间的差异被明示，这样我知道能力边界。
14. 作为 Team 成员，我想无权限成员不能交接到其无权访问的 Project。
15. 作为 Team 成员，我想交接被拒时不留半成品 Task。
16. 作为 Team 成员，我想 Run 成功不自动 done，完成仍按审查策略显式提交。
17. 作为审查者，我想 Task 的审查要求由任务钉选、项目默认、平台默认依次决定，空值不放宽。
18. 作为 Team 成员，我想协调会话在交接后继续可用，讨论不被关闭。
19. 作为维护者，我想项目管理写操作有逐项授权白名单、作用对象与审计；已有目标授权可覆盖多步管理，不把通用管理员权限交给 Agent。
20. 作为维护者，我想矩阵区分获授权的项目管理写入与被拒绝的直接实施工具，不将“协调只读”误用为永久禁止任务管理。
21. 作为维护者，我想同候选下 server / worker / web-next 测试与三个 e2e 全绿。
22. 作为维护者，我想至少一个有效 Runtime 的真实执行证据（本地或免费模型）。
23. 作为维护者，我想未覆盖的 Runtime 与能力差异如实标注，不冒充已覆盖。
24. 作为 Team 成员，我想取消或失败的执行在协调上下文可见并带原因。
25. 作为审计者，我想每次交接与启动都留下可复查记录（主体、目标、revision、来源）。
26. 作为维护者，我想验收摘要入库、原始证据留 `.scratch/`，并区分已实现、已验证与未完成。

## Implementation Decisions

- 计划 revision 不可变、编号递增，含创建者与时间；批准是独立记录（revision、批准人、时间）；新 revision 不继承批准。存储沿用现有文档 CAS 与 requestId 幂等约定。
- 交接操作授权、幂等、原子：一次请求内创建普通 Task（含计划引用、验收标准、来源协调 Task/Session 引用）；重复 requestId 返回同一 Task；失败不留半成品。
- 创建与启动分离是内部执行合同，不是两个用户步骤：按已确认 D1，backlog 不派发，todo 状态驱动派发；创建 todo 同样需执行安排权限及适用的计划批准。任务创建、状态迁移和实际启动各有可追溯幂等身份；可靠恢复状态事件，启动失败不伪报任务不存在或重复创建。
- 能力面变化：只开放逐项定义的项目管理操作，包括任务组织、依赖/阻塞管理、执行安排和结果跟踪；必须绑定实际授权人、范围与当前资源权限。管理角色不获得普通实施文件/终端写权，也不得自行批准自己受限制的操作、扩大范围或取消审查。逐项更新能力合同与写通道矩阵，不用万能管理令牌。
- 交接目标校验：成员资格 + 目标 Project 访问权 + Task 归属；无权限 fail-closed，不泄露目标元数据。
- 来源可追溯：Task 保留来源引用；协调会话可查询关联 Task / Run / Session 状态与结果。
- D6 交互：本次讨论/制定计划/执行意图、项目管理 Agent 职责授权、成果审查分别表达，不强制两种自治模式前置表单。用户通过项目配置职责与授权并交代目标，Agent 维护同一任务图；手工看板独立可用。服务端按操作校验权限，不以角色描述或模式标签替代能力限制。01 实现交互和授权，02 分项 B 按已确认事件与暂停合同交付持续推进：用户目标/要求、完成/审查通过/依赖解除触发相关检查，机器/容量交调度器；不做无事定时巡检，事件持久去重、重启恢复不绕过授权与暂停。暂停管理 Agent 停止新增安排，在途取消另行操作；首版不强制期限/金额预算，新增付费服务或扩大授权需确认；可得费用如实显示、不可得标未知，不承诺硬控费。自动截止/金额硬上限属后续独立能力，不阻塞本次持续推进。人、主 Agent、执行 Agent 通过同一获权任务接口表达状态及提交成果，平台不从 Run 退出或测试红灯推断任务失败。主 Agent 对照目标与成果识别剩余工作：同目标在原 Task 继续或新 Session 接手，独立额外工作才创建有验收要求和来源关联的后续任务，不设任务失败次数或自动重试循环。
- Task Progress Record：同一 Task 可追加多条任务进度记录，保存进展、剩余事项、问题、成果/验证引用和接续建议，保留作者及来源 Session/Run。内容约定参考 Matt handoff 的接手目标、上下文指针和脱敏原则；记录直接承担交接上下文，不另外复制成报告，也不自动变更状态。正文明确发布给可读取 Task 的人和 Agent，不再要求来源 Session 读取权；来源引用和自动预览仍独立鉴权，不自动搬入私有会话内容。01 实现持久记录/API/任务详情，02 分项 B 验证原任务新 Session 接手；同目标继续不强制新建 Task，额外独立工作才另建。执行 Agent 只记录实际进展与困难，不主动发出接手请求；主 Agent 或获权的人决定是否接手及接手者，明确安排不以执行 Agent 请求为前置。
- 审查：沿用 `resolveReviewRequirement`（Task 钉选 → Project 默认 → 平台 none）。项目设置默认，任务提供沿用/无需/需要人工审查及适用的多级配置；只有有权限的用户或管理身份能设置，执行 Agent 不得自行降低。开始执行时固定有效要求，项目默认变更不影响在途任务。无需人工审查仍显式提交成果及验收证据，Run 成功不自动 done。
- 依赖：任务管理 Module 权威维护任务完成依赖及其满足状态，向执行 Interface 提供带版本的资格及等待原因；不以自由文本 `blocked` 代替关系。需要审查的前置任务尚未通过时不满足完成依赖，互不相关任务仍可推进。取消/删除不冒充完成；更多依赖类型与跨项目范围另做合同设计，不默认扩大。
- Runtime 适配：通过各 Runtime 适宜的工具入口暴露同一组操作（查询、交接、执行、报告），差异（能力、入口形态、认证）在验收文档中明示。
- 结果回写：以引用形式回写协调上下文，不复制执行现场。

## Testing Decisions

- 复用现有 seam：任务创建与查询 API（幂等、CAS）、协调 Task 查询操作、Web 协调与普通 Task 界面、既有 Runtime 会话启动路径、现有 e2e 骨架。
- 只测外部行为：revision 与批准状态可查、旧批准失效、重复交接幂等、无权限 403、无半成品、backlog 不派发、todo 无需二次确认参与派发、Run 成功不 done、结果引用可查。
- Prior art：现有幂等与 CAS 测试、审查策略测试、协调入口浏览器用例、跨 Runtime 会话启动骨架。
- 真实执行：至少一个有效 Runtime 用本地或免费模型完成查询 → 交接 → 执行 → 报告只算增量证据；NEXT-08 关闭必须逐个验证 pi / claude / opencode 的实际有效入口。未覆盖项保持未完成，不能用 test-agent 或单一 Runtime 代替。

## Out of Scope

- 未获授权的自动启动、自动批准、Run 成功直接 done；授权范围内的持续推进属于本 spec，不因该排除项被取消。
- 新增 Runtime 适配（Codex 属 FUTURE-01）。
- 付费模型签收。
- 画布、连接器、双宿主与切根工作。

## 实现计划

任务管理可替换是已确认要求：本 spec 的 Web 与 Agent 操作均经过任务管理 Module 的稳定 Interface，现有 TaskService 作为内置 Implementation；不向调用方暴露具体看板存储或外部 SDK。任务来源标识、状态映射、授权及版本回写合同与[派发 01](../web-next-task-dispatch/issues/01-placement-claim-dispatch.md)共用，替换项目管理系统不得换绑历史 Run/Session 或绕过批准策略。具体外部产品尚未选定。

1. 盘点现有 Task/Run 应用操作与 Agent API，只为缺失的任务更新、依赖/阻塞、执行与结果查询补合同；Web 与 Runtime 入口共用同一授权/CAS/幂等实现。由本 spec 的 01 实现依赖存储、授权编辑和查询（含自依赖/循环拒绝），以及项目默认/任务覆盖审查界面；派发 01 仅消费资格合同，不反向依赖本票整体交付。
2. 在现有计划文档存储上补 revision 与按需批准、原子交接和来源引用；分别测试 backlog 暂存、获权创建/推进 todo 自动参与派发和要求先审计划三条路径。
3. 项目管理工具将执行意图交给任务派发 Module，不在 Runtime 内再实现第二套机器调度。状态驱动、容量分配与重新分配遵循已确认 D1–D3，未配置容量的初始化值仍待明确；既有指定机器手工链路不等待新增自动调度。
4. 按各 Runtime 能力提供适宜入口，增加有界的进展/阻塞跟进与结果引用；按已确认事件合同唤醒并验证暂停/撤权，不以无限循环代替。复用可得费用数据并标明未知范围，不为首版额外建设硬预算系统；自动截止与金额硬上限后续单独跟踪。
5. 01 交付管理合同与按需交接；02 交付真实跨 Runtime 闭环、授权撤销和人工介入验证，再提交人工签收。协调 UI 开放仍依赖独立开门票，离线合同开发无需提前开门。
