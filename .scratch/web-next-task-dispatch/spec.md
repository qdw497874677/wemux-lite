# 项目看板与团队远程任务派发

Status: ready-for-agent

## Problem Statement

当前资源管理和计划交接规格没有完整覆盖用户已明确的核心用途：团队从项目看板管理任务，把执行交给符合条件的空闲远程机器，既允许候选范围内申领，也允许指定机器。现有指定 Worker 的 Assignment 不等于多候选调度、容量预约或多用户公平使用已经存在。

## 需求来源与范围

依据[需求基线](../../docs/specs/ai-workbench-requirements-alignment.md)条目 1–7、9。Vibe Kanban 只提供工作视图参考，不能作为远程调度已被验证的证据。

- Task 声明可执行机器范围：所有获权且符合条件的 Worker、指定候选集合、固定 Worker。
- 用户或获授权的项目管理 Agent 可以指定派发；开放执行意图允许符合条件的 Worker 申领。
- 看板按需求基线 D1 驱动普通 Task Workflow：backlog 暂存，todo 参与派发，实际启动后 in_progress；blocked 暂停推进，in_review 按审查策略处理，done/cancelled 不再派发。无独立入队开关；卡片/详情另呈现等待原因、实际 Worker、执行状态及成果，不用机器状态替换任务状态。
- 多用户同时创建/安排工作，权限、容量与执行归属保持一致。CPU/内存属于 Agent 与工具执行资源，不涉及模型推理调度。

## 已确认默认与实施前置

需求基线 D1 状态驱动、D2 首版容量/分配规则及 D3 重新分配/先对账恢复规则已确认。Worker 未配置时默认 1 个执行槽位，机器管理者可配置并发上限，首次接入无需先填配置；本地/集群以及普通执行/接手共用容量，CPU/内存不自动提高上限。无可用机器/容量时普通任务保持 todo、接手保持 in_progress 并显示原因，不另加排队 Task 状态。`ready-for-agent` 不代表实现或验收完成，具体前置与人工门仍见票据。

## 用户故事与验收目标

1. 我可以从看板创建/继续任务、手工进入多个会话，不必经由协调 Agent。
2. 我可设置任意候选、候选集合或固定机器；无权机器不在可见选项内，直接 API 请求也不能绕过。
3. 我能看到为什么未执行：尚处 backlog、机器不可用、无容量、Runtime/模型不可用、Placement 未就绪或权限失效。
4. 符合条件的 Worker 申领同一执行意图时仅一个成功；平台重启、并发请求和传输重放不重复启动。
5. 指定派发和开放申领使用同一权威分配记录和容量预约，不互相绕过。
6. 一个 Task 可以有多个明确安排的执行及 Session；互斥对象是一次执行意图，不是永久锁住 Task。
7. 团队成员的 Worker 使用权、Project 操作权和 Session 内容/控制权分别判断；Agent 调用保留实际授权主体。
8. Worker 加入集群只提供获权执行能力，不泄露其他用户的本地会话、路径、凭据或成果。
9. 断线后结果不明的已承接执行不得仅凭租约过期就在另一机器重复启动；重连先核对原运行事实。
10. 修改 Task 的候选范围只影响后续分配，不换绑已存在的 Run/Session；尚未派发可重新选机。同一目标换执行者时，获权主体可明确安排原 Task 的新 Session 接手，Task 可保持 in_progress；该接手意图单独校验权限、依赖、容量及旧执行事实，不依赖把任务退回 todo。额外独立工作可另建 Task；派发器不提供任务自动重试，不迁移原会话。
11. Worker 空闲但所需代码/环境未准备好时不能伪报可执行；跨机使用须明确仓库版本与 Placement，不隐式同步未提交变更。
12. 权限撤销阻断后续分配/启动；在途工作按控制合同停止或报告无法确认，不宣称撤销能回滚已发生的副作用。

## 任务管理与执行解耦

- 任务管理 Module 负责项目/任务、工作流、目标与验收要求；执行 Module 负责执行意图、机器匹配、容量、Run/Session 及执行事实。内置 Kanban 经同一 Interface 使用任务管理能力，不直接操纵执行表。
- 在任务管理与执行之间建立可替换 Seam。Adapter 将来源任务标识、版本、状态和授权上下文映射到稳定合同；D1 是内置工作流映射，调度不能依赖外部系统的列名或状态枚举。
- 每个接入任务明确唯一状态权威；执行事实通过带版本的受控回写推进任务，冲突重读、不覆盖新状态，不维护两个可任意互相覆盖的任务账本。来源标识与本地稳定绑定保留，使历史 Session/Run 不因替换而换绑。
- 任务管理侧提供依赖满足状态及版本化执行资格；普通状态驱动派发要求 todo；显式接手允许 in_progress，必须经同一 Interface 检查接手资格而非绕过 Adapter。前置未完成（含仍待人工审查）不得承接/启动；blocked、in_review 和终态不得借接手请求绕过工作流。依赖解除不把 backlog 自动改成 todo。依赖存储与编辑归项目管理票 01，派发负责在承接和启动授权时重新核验，双方先冻结共同合同，不互设整票依赖。
- 外部状态事件不直接授权执行，仍校验操作者/委托、机器权限、最新版本和幂等执行身份。重复、乱序、断线及回写失败可恢复，不能因此重复启动。
- 本轮交付内置 Adapter 和可替换合同，通过另一组异构状态/标识的测试 Adapter 验证 Seam；测试替身不代表真实外部集成完成。具体外部项目管理产品、同步方式与切换迁移另行确定，不提前建设通用插件平台。

### 接手共同合同

- 接手绑定被接替的执行身份及接手代次，原子认领该接替关系；不同 requestId 竞争同一代接手只能一个成功，不以永久 Task 单执行锁代替。
- 确认旧执行停止只是必要条件，还需阻止旧执行权、旧 Session 已排队和迟到消息在交接期间重新启动。无相关控制权限或无法安全对账则等待；原 Session 历史保留，将来明确继续须重新获得有效执行权。
- 等容量的显式接手意图持久化，Task 可保持 in_progress，容量/机器恢复须重新匹配该意图而非仅扫描 todo。接手与普通任务统一按本次执行安排入队时间排序：普通任务进入 todo 时入队，接手在明确安排时入队，无特殊优先级，不套用旧 Task 的 todo 时间，也不要求退回 todo。仅匹配符合资格的工作；旧执行未确认停止则显示等待原执行确认。入队顺序持久化，重复事件及重启不重排。
- 派发 01 负责共同 Interface 合同，项目管理 01 提供进度记录与有效审查快照的领域定义；双向合同先冻结，非整票循环阻塞。任务管理 Module 权威保存记录身份及 Task 冻结审查策略，Interface 暴露获权追加/查询及有效策略读取；外部 Adapter 不必原生存储，但不得丢失稳定绑定或另造权威。接手沿用冻结策略，不重新解析已变更的项目默认。

## 实现计划

1. **合同与数据**：在 Task 执行意图与 Run 不可变快照之间定义机器范围、排队/承接记录和容量预约；沿用 requestId、CAS、SQLite 事务保障本地记录；先冻结上述任务管理 Interface，再实现内置 Adapter，不假定未来外部任务系统能加入同一 SQLite 事务。不把 User 指派、Worker 选择、Runtime 选择混成一个字段。
2. **匹配与分配 Module**：Server 内提供小 Interface 承接“请求执行、尝试承接、撤销、查询原因”；隐藏匹配、原子预约与恢复。Worker 只能以自身身份请求承接，不能自报他人授权；由 Server 检查最新资源权限并签发受限执行。
3. **容量与本地准入**：按已确认 D2，由机器管理者设置最大并发执行数，本地/集群共用；可用候选优先剩余容量比例高者，符合条件工作按本次执行安排入队顺序处理（普通任务进入 todo，接手明确安排），不引入团队配额或复杂优先级。Worker 报告带采样时间的资源和执行槽占用，区分本地宿主与集群运行但不上传本地内容；Server 预约不是 OS CPU/内存配额，Worker 启动前再次检查，不能只凭陈旧心跳超卖。
4. **持久恢复**：先预约、再可靠投递、确认承接/启动，所有状态可追溯；复用已有稳定领域身份与 outbox。区分未承接可释放、已接受结果未知、已结束可释放，增加陈旧承接请求拒绝与恢复对账，不宣称通用 exactly-once。
5. **看板/API**：在现有 ProjectTasks、TaskCreateForm、TaskDetailPanel、TaskRuns 中增加范围、状态推进、等待原因与运行位置。用户拖动看板和 Agent 更新状态共用授权入口；进入 todo 可靠产生执行意图，无第二个入队开关，实际启动确认后才进入 in_progress。
6. **团队验证**：两用户、两 Worker、至少两个 Task 的容量竞争、权限撤销、断网/重启/取消与恢复；加入目标机器忙碌、能力变化、共享 Placement 写冲突和无权限元数据过滤用例。

## Testing Decisions

- 状态行为测试覆盖创建 backlog 不派发、创建/迁移 todo 自动参与派发、无容量仍 todo、实际启动才 in_progress、阻塞/终态停止后续派发；重复事件及重新进入 todo 核对在途工作，不重复启动。Run 成功不直接完成，成果提交按审查策略处理。
- 接手负例覆盖不同 requestId 竞争同一接替代次、旧 Session 排队 Turn、迟到消息重放、重启及撤权；等待容量后仅一个接手恢复，不重启旧执行。内置与异构 Adapter 均验证 in_progress 接手与非法状态拒绝，并保留已有多条记录和冻结审查策略。
- D3 覆盖未派发的固定机器离线等待/候选重新选机，已派发启动未知或执行中失联先对账；恢复核对进程、记录与结果后才决定跟踪或释放。后续 Task 的新执行检查代码/Placement；改范围、重入 todo 或换 Task 标识都不能绕过对相关未知执行的安全核验。连接恢复和幂等重投不等于任务自动重试。
- 纯匹配测试不替代真实持久竞争与 Worker 执行：SQLite 事务并发申领测试、真实 WebSocket 重放/故障注入、子进程启动计数与 Run/Session 身份断言。
- 真实浏览器覆盖桌面/手机：创建任务、候选设置、开放申领、指定派发、容量忙碌、停止、查看结果；测试使用本地桩/免费运行时，不授权付费调用。
- 用至少两台可区分的 Worker 进程验证机器路由；本机多进程只证明协议链路，不冒充异构远程宿主验收。最终异构真实机器证据另列环境并保留未覆盖项。
- D2 验证本地/集群竞争、剩余容量比例选机、普通任务和接手统一按本次安排入队顺序处理，接手不借旧 todo 时间插队；指定机器忙碌不暗换。CPU/内存不是硬准入或资源配额保证；验证未配置默认 1、获权修改上限及重启后配置保留；恢复技术参数不冒充产品容量配置。
- 依赖负例覆盖前置待审查、取消/删除、资格过期和重复解阻事件；依赖解除使已有 todo 执行意图及已明确安排的 in_progress 接手意图重新参与匹配，不启动 backlog，不新建或重复执行。真实依赖编辑及审查联动由项目管理 01 与本票联合验收，合同测试可分别先行。
- 同一任务管理 Interface 合同测试覆盖内置 Adapter 及异构状态/标识的测试 Adapter；核验授权、版本冲突、重复/乱序事件与回写失败，不通过看板或任务存储内部字段测试执行逻辑。

## 边界与依赖

- 不迁移既有 Session，不做共享文件系统、自动凭据同步、抢占调度或模型算力编排。
- 复用资源管理的真实探测、命令授权、Task/Run、Worker 可靠投递与既有授权基线；指定机器手工使用不依赖协调聊天开门。
- L1 不构成不互信团队之间的 OS 隔离；共享机器的部署信任边界必须明确。
- 本 spec 是新增目标，NEXT-03/04 历史签收不覆盖它。已确认 D5 将本 spec 及可替换任务管理合同纳入迁移和切根范围，未完成不能用旧完成数字掩盖。
