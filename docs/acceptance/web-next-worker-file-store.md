## Integration API and mandatory ordering

- `store.fileWrites.get(requestId)` and `listPendingResults(limit)` are committed-only FIFO readers, not transaction readers. Do not await them inside a transaction callback.
- `tx.fileWrites.reserve(admission)` verifies through `@wemux/wire-protocol/file-admission-node`, captures immutable primitive snapshots synchronously before yielding, and keys solely by the Server admission identity `requestId`. All provenance, binding, content, path, version and fingerprint fields are retained exactly, without normalization. Property insertion order is not identity. Same requestId with changed valid input returns `reject/identity-conflict` without overwrite; malformed or hash-invalid inputs throw.
- A new reservation returns **provisional** `execute` inside the callback. Only the successful resolution of `await store.transaction(tx => tx.fileWrites.reserve(snapshot))` grants the caller a committed decision. Never perform I/O, invoke effect callbacks, publish results, or use a leaked decision inside the callback. A rejected/rolled-back transaction grants no execution authority. This is a caller-ordering invariant, not a type-enforced prohibition on malicious callback I/O; the supervisor explicitly confirmed this composition contract. Future Runtime must snapshot before its own asynchronous authorization/queue boundaries and consume only the successful outer return value.
- Identical unresolved duplicates return `await-existing`; retained results return `replay` or `unknown` with exact retained `resultJson` and digest. Unknown is uncertainty, never success, permission to retry, or settlement authority.
- `tx.fileWrites.retainResult(result)` uses the approved Node parser to verify admission identity, SHA-256 result digest, outcome schema, and success path/size. It inserts result plus pending application-result delivery atomically. A trigger and savepoint protect the pair even if SQLite `ABORT` or `FAIL` is caught by the callback. Exact duplicate retention is inert; changed retained results throw permanently, including unknown-to-success changes.
- Publish only committed pending results. No publication occurs here. `tx.fileWrites.acknowledgeResult(ack)` verifies the complete application ACK against the retained result using the Node subpath. Matching ACK marks delivery acknowledged; duplicate ACK is idempotent. Admission, result, and acknowledged delivery remain permanently retained as dedupe tombstones, even after Session deletion. ACK does not resolve unknown. Transport ACK, timeout, reconnect, and sending never clear application obligations.
- `tx.fileWrites.recoverUnresolved()` is explicitly for the exclusive runtime lifecycle owner after prior execution has stopped. It converts all unresolved reservations to verified retained unknown results plus pending delivery in one atomic operation; errors caught by the enclosing callback still roll back the entire recovery batch. It grants no re-execution or takeover permission. There is no production caller and no new operational authority established by this API.

Transactions now issue per-callback leased writers; escaped writers reject after commit/rollback, including during later transactions. Existing Session/queue/Journal operations retain their transaction behavior. Schema migration appends versions 6 and 7 from schema 5; read-only opens accept existing supported schemas without migration or recovery. Normal writable reopen migrates as needed but never recovers reservations. Schema 5 diagnostic callers may use pre-existing readers; file-admission readers require schema 6. SQL insert guards prevent replacement of immutable rows and delivery with `recursive_triggers=OFF`; update/delete guards preserve retention and monotonic ACK.

Integrity verification is not authenticated-origin or Workspace authorization. Future Runtime still must verify connected origin, local Worker/Session binding, Workspace eligibility/readiness, sandboxing and execution ordering. No exclusive Workspace writer claim is made.

## Review correction: explicit SQLite rowid replacement

Independent review of the preceding implementation returned **BLOCK** for P1: ordinary SQLite tables have a unique rowid in addition to `request_id`. With `recursive_triggers=OFF`, `INSERT OR REPLACE` targeting an existing explicit rowid but a different valid requestId could erase an unresolved admission without firing the delete guard. A real temporary-database regression reproduced the defect before the fix: the original duplicate returned `execute` rather than `await-existing` (1 failing test, exit 1). Prior 18/37-test validation did not cover that path and was not acceptance of the flawed guard.

Append-only **schema 7** installs additional insert-collision and rowid-update guards on all three file tables. Existing schema 6 table definitions and triggers are unchanged; no table rebuild, byte rewriting or ordering redesign occurs. Rowid aliases (`rowid`, `_rowid_`, `oid`) resolve to the same guarded identity. RequestId guards remain in force. The application ACK update is still permitted, but delivery rowid movement is not. Existing schema6 databases install this migration on writable reopen; read-only opens do not migrate or recover.

The supervisor approved reserving persisted **rowid -1** as an internal storage invariant, not a public SQL compatibility promise. SQLite supplies `NEW.rowid=-1` to BEFORE INSERT for automatic allocation, so an AFTER INSERT guard checks the actual allocated rowid and raises `ABORT` for a persisted -1. Ordinary positive automatic inserts still work; failed sentinel inserts roll back the complete statement and trigger side effects. Before installing any schema7 guards, migration checks all three tables for existing -1 rows. If found it fails closed with `Worker schema 7 migration refused: <table> contains reserved rowid -1`, leaves schema version/data unchanged, and performs no repair or recovery. Read-only diagnostics remain available.

**Out-of-band negative-rowid limitation:** a database externally changed so that a table's maximum rowid is -2 may pass migration, but its next automatic allocation can be -1 and therefore fails atomically with `File storage rowid -1 is reserved`. This does not grant a committed execute decision or change the existing reservation. Arbitrary negative-rowid SQL allocation is not supported by this slice; the migration does not reject every negative-rowid state or silently renumber it. Normal Worker-port-generated positive rowids are unaffected. No operational repair authority is introduced.
