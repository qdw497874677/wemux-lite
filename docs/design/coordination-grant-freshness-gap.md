# Coordination grant freshness: partial implementation boundary

Ticket: [coordination 01](../../.scratch/web-next-coordination-closure/issues/01-session-scoping-and-gateway-binding.md). This note is investigation, **not** a grant freshness acceptance or permission to open the coordination gate.

## Observed identity flow

`ServerService.enqueueInTx` generates a Turn ID in `apps/server/src/application/server-service.ts` before persisting the enqueue command. The signed claims in `packages/domain/src/capabilities.ts` and `CapabilityTokenService` include Session ID, Turn ID, Project ID, Workspace ID, actor identity/version, tools, and Connector IDs, **but no Worker ID or immutable binding generation**. Worker stores the grant Turn ID with the queued message and persists a `Turn` in its own SQLite database; its Connector runtime checks that the local persisted Turn is `running` and matches its current Session/Worker/Workspace. Server does not persist a Turn row. It projects `activeTurnId` from the received `turn.started` and `turn.finished` Journal events in `ServerService.executionState`; the Journal observation can lag the Worker, including before a started event arrives.

`POST /api/agent-capabilities/grant.verify` calls `CapabilityService.verify`. Today it checks the signature/expiry, allowed tool, existing Session and matching Project/Workspace, Task availability, actor version/access and current Worker access for Connector tools. It does **not** compare the grant Turn ID with a currently observed active Turn or bind the token to the original Worker. Comparing only a current Session Worker to a token without Worker identity is a tautology; comparing Journal `activeTurnId` synchronously would reject a valid Worker call before event delivery and does not establish fresh authority across transport disconnection. A Worker-side running Turn check does not prove that the Server's original binding still authorizes the call.

## Required follow-up before claiming complete enforcement

Version the signed claim/runtime payload contract to include the issuance Worker ID (and preferably a binding generation) and verify against the current Session placement; define compatibility behavior for already queued commands, restarts, local-host capabilities and transport reordering. Specify a durable Server-side Turn lease/acknowledgment or an explicit freshness protocol rather than assuming immediate Journal observation. Recheck at post-approval/pre-dispatch and cached replay. Route-level integration tests must exercise successful ordinary query and Connector grant, expiration, actor revocation, completed Turn and moved Worker binding (including pre-start event delivery and out-of-order observations). No shared protocol modification or speculative Server-only `activeTurnId` check was made in this partial ticket.

## Denial audit status and remaining gap

Worker schema 8 migrates the previously unversioned `connector_denials` table into a versioned, transactional policy retaining the latest 10,000 rows, pruning older rows on migration and insert. This bounds row count (not total DB file size; SQLite may retain pages until vacuum). `ToolExecutionGateway.auditDenial` logs a storage error instead of silently swallowing it; the denial remains denied. Audit storage is still best effort: a crash, full disk, failed write, disabled optional store, or overwritten retention window may leave no durable record. Logs are not guaranteed durable. A guarantee that *every* denial leaves a durable audit requires a fail-closed durable audit admission path and an operator-visible health/retention/export policy, separately designed and tested; the present partial implementation does not satisfy that ticket checkbox.
