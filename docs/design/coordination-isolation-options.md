# 协调 Runtime 隔离：环境方案决策简报

**状态：待用户决策（2026-10-08）。本文件不构成选择、不构成风险接受，也不改变门禁。** 依据 `.scratch/web-next-project-agent-platform/evidence/ticket-05-runtime-isolation-gate.md`（判定 FAIL）与 `.planning/phases/02-agent-api/02-CONTEXT.md` D-01/D-02；口径见 `docs/acceptance/web-next-phase2-controlled-slice.md`。

## 要解决的问题

开放 Team 协调入口前，必须让"被引导的协调 Runtime 读不到 Worker 凭据与实现仓库、也无法把读到的内容外发"这件事由**操作系统或网络层强制**，而不是靠提示词或工具白名单。当前本机两类强制层都缺失：

| 强制层 | 现状 | 影响 |
| --- | --- | --- |
| 文件面（只读/隐藏） | 无 namespace、无只读绑定、无 Landlock、不能降权 | 协调身份可读 `<home>/credential`、`transport.sqlite`、整个仓库与 `.scratch` |
| 网络面（出口收敛） | 代理变量只是建议；无 netns；公开邮件入口无法阻断 | 读到的内容可被直接外发；无法阻止触发注册/找回邮件 |

已具备、但**不构成隔离**的三层：Server 只读能力面、签名 `allowedTools` 声明、Pi 启动参数 `--tools`/`--no-extensions`/`--no-skills`。它们只降低写入与 shell 执行风险。

## 五个环境方案（gate 证据 §五，按代价从低到高）

| # | 方案 | 需要什么 | 谁能做 | 覆盖 | 代价与限制 |
| --- | --- | --- | --- | --- | --- |
| O1 | 安装 `bubblewrap`（或 `firejail`/`proot`） | 包安装权限（本机 uid 10000，无 root） | 宿主/部署方 | 文件面（`--ro-bind`/`--tmpfs`）+ 网络面（`--unshare-net` + 显式代理白名单） | 低。需为 Worker 进程包一层启动封装，Worker CLI 与 e2e 骨架都要改；`proot` 隔离强度弱于 bwrap |
| O2 | 放开非特权 user namespace | 宿主 seccomp/容器策略允许 `unshare -Ur`（当前被拒，配额存在） | 宿主/平台方（本沙箱内不可自助） | 文件面（只读绑定）+ 网络面（`unshare -Urn` 断网） | 低到中。不装新包，但依赖宿主策略变更，变更者需理解容器安全影响 |
| O3 | 内核启用 Landlock | 内核支持 `landlock_create_ruleset`（本机 `Function not implemented`） | 宿主/内核方（换内核或换宿主） | 文件面（可写/可读路径限制），**不含网络面** | 中。需内核版本与 LSM 支持；单独用不足以收敛出口 |
| O4 | 独立低权限系统账号 + 出口策略 | root 配置账号、文件权限、`iptables`/`nftables` 或透明代理 | 宿主 root | 文件面（文件权限隐藏凭据与其他项目）+ 网络面（防火墙/强制代理） | 中到高。运维面变大：账号与防火墙成为部署前置；proxy 需强制而非建议 |
| O5 | 协调 Runtime 放到独立宿主/容器 | 第二台宿主或容器平台，Worker 仅作控制面 | 部署方 | 两面（由外部环境边界提供） | 最高。最彻底，也最重；跨宿主网络与身份链要重新设计 |

**组合与现实约束**：O1 单独即可覆盖两面并重跑本门；O2 可替代 O1；O3 与 O4 必须组合（Landlock 无网络面、账号方案需防火墙配合）；O5 独立成立。本沙箱内五个方案**都无法自助实施**（无 root、宿主策略与内核不可改），因此环境变更必须由你或宿主方执行，之后我再按探针集重跑门。

## 岔路（gate 证据 §六）

| 选项 | 内容 | 前置条件 | 后果 |
| --- | --- | --- | --- |
| **A（当前默认）** | 协调入口保持不可用；Ticket05 in-progress；Ticket06 前置门不解除；先做不依赖协调 Runtime 的票 | 无 | 阶段 2 保持 OPEN；可继续其它票据的独立余量 |

## 你做出决定后会发生什么

**若选环境变更（O1…O5 任一项或组合）**
1. 由你或宿主方实施变更，并提供可复现的变更说明（安装包、策略、内核/账号/防火墙配置）。
2. 我按 gate 证据 §二/§三 的真实系统调用探针 + `apps/e2e/coordination-write-channel-probes.mjs` + `apps/e2e/next-worker-reconnect-pairing.mjs` 重跑，逐项给出退出码。
3. 门通过后：解除 Ticket06 前置门 → 可开放受限协调执行 → 重跑并更新写入通道矩阵（D-06）→ 落地两项缺口责任票（Worker 网关 `allowedTools`/binding 校验、命令帧授权审计）→ 票05 才具备整票验收条件。

**若选 B**
1. 你出具书面风险接受范围（环境、账号、可读目录、数据边界）。
2. 我先把两项缺口票修掉（它们是无条件该修的），再按 B 的条件开放受限入口。
3. 文档与界面必须写明"未隔离"，不得出现"已隔离/安全"表述；矩阵相应行从 `documented-gap` 改为"接受的风险"并注明批准人。

**若维持 A**
1. 阶段 2 继续 OPEN，不做完成宣告。
2. 转去其它不依赖协调 Runtime 的独立余量（票 11/13 等，需先做依赖与差异核对）。
