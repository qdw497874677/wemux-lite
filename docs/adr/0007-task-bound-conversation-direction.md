# 产品对话要求 Session 绑定 Task

访谈已确认新的产品方向：常规对话的 Session 必须绑定 Task，不再将无 Task 的直接对话作为常规产品路径。此决定改变了此前“Task 是可选入口”的产品假设，不只是 Paperclip 外观或前端交互迁移；相关后端约束、领域术语与产品文档须在合同明确后同步调整。

测试或快速试聊场景也必须绑定 Task，采用自动提供专用 Task 的方式，而不开放无 Task 对话例外；用户可以直接开始测试，不必先填写普通任务表单。此方向参考 Paperclip Agent Chat 自动创建专用 Issue 的做法，但不直接照搬其唯一键、状态机或权限规则。

专用 Task 按“用户 + Project + Workspace + Worker + Agent + 场景”组合复用；同一组合可在任务内新建多个 Session，不同组合不共用专用任务。Model 不进入专用任务复用键。用户后续明确允许同一 Session 切换当前 Agent 的模型，不要求另开 Session；须保留每次执行实际模型的记录，切换生效时机另行细化。这不等于允许切换 Agent、Worker 或换绑 Task。此自动复用规则不限制普通 Task。

Session 一旦绑定 Task，不允许日常换绑，不提供会话迁移入口；要在其他 Task 继续工作，创建新的 Session，原记录留在原 Task。本次不因此新增跨任务上下文复制功能。

历史数据策略已变更：用户明确允许历史数据全部清除，不再要求迁移旧会话、补建历史任务或保留旧业务记录。实施按全量应用数据重置规划，需列明 Server/Worker 数据清单及账号、注册身份的重建步骤，不能假设旧身份在重置后仍可用；用户允许直接清理，不要求等到最终切换才清理；整体访谈尚未确认完成，因此本阶段仍不执行删除，进入实施前列明受影响数据与重建顺序。应用历史数据清理不等于删除项目源码、外部仓库文件或机器上其他应用的数据。

双宿主执行一致的 Task 绑定规则：集群 Session 绑定 Server 管理的 Task；Worker 独立工作台 Session 绑定 Worker 本地管理的 Task，并支持自动提供专用测试任务，不依赖 Server。Worker 加入集群不自动上传、合并或改变本地 Task/Session 的归属，两种宿主各自鉴权。实施需补齐 Worker 本地任务能力，而非只添加界面标签。

执行权限已确认参考 Paperclip：专用对话任务主要用于讨论、研究、计划和交接，正式实施工作交给普通 Task 执行。由运行时强制限制，而非仅依赖提示词：允许读取、搜索、分析、保存计划、创建和关联普通任务；禁止修改工作区代码、安装依赖、部署及调用具有外部写入副作用的工具。无法可靠约束副作用时，不开放任意 Shell。普通任务按授权开放实施工具，仍遵守审批规则。此变化不允许把已有 Session 换绑到普通任务，须在目标任务新建 Session；交接授权参考已核查的 Paperclip AGENT_CHAT_DIRECTIVE：用户意图与实施范围已经明确时，不要求仪式性的重复确认；若用户要求先审批计划，必须保存计划并生成绑定具体 revision 的确认记录，计划修改后须重新确认新 revision。已接受的计划允许交接给普通实施任务，由任务在获授权范围内执行，不要求对同一范围再走一轮独立执行批准；原有工具审批和范围变更仍需相应授权。普通任务携带来源对话、获批计划版本、接受记录和相关计划内容，不将复制后的新计划伪称已经单独获批。讨论任务不得因此直接实施。此处借鉴的是源码中的对话指引，不能将该指引本身当作 Paperclip 已提供全部运行时强制校验的证据。

计划交接采用方案 A：已交接普通任务固定使用交接时的计划版本，原对话继续修改草稿不自动改变任务。改变执行范围须显式更新任务并按需重新授权，由执行边界校验，不能把新草稿视为原批准的一部分。

平台位于具体 Agent Runtime 之上，不以 Pi 特有接口定义平台任务语义；可通过适配层接入 Pi、Claude Code、OpenCode、Codex 等运行时。平台拥有 Task、计划批准、执行授权与审查合同，各运行时保留自身内部任务管理方式；Skill、CLI、原生工具或 MCP 是可选接入形式，不代表所有运行时已实现支持，也不要求每个运行时具备所有形式。已确认参考 Paperclip 的适配方式：采用多入口、统一平台能力、按 Runtime 适配，不强制所有运行时通过 MCP。Adapter 负责进程启动、会话恢复、事件与取消，并按能力注入 Skill 指引和 CLI/API、MCP 或原生工具入口；所有入口遵守同一平台授权、幂等和审计规则，不分别实现任务业务。集群控制路径仍遵守 Wemux 的 Worker 边界，不为各 Runtime 另建集群身份。Skill 不是安全边界，禁止任意 Shell 的讨论模式不能把依赖任意 Shell 的 CLI/curl 作为唯一入口。具体运行时支持范围与讨论权限的强制执行能力须分别验证。

首批运行时验收采用方案 A：迁移并验收当前已有的有效适配，不因架构支持多 Runtime 而把新增 Codex 接入列为此次新版切换门槛。Codex 后续独立交付；现有实现须核实实际有效能力，不能只凭适配文件存在宣称支持，讨论权限约束仍逐运行时验证。

对话创建实施任务的独立开关方案已被后续决定取代：与已核查的 Paperclip 对话指引保持一致，不增加独立开关，依当前模式、用户意图与授权判断是否可创建和交接普通实施任务；纯讨论不自动派发。承载对话的专用 Task 仍自动提供，Runtime 内部任务工具不因此被替代。

已确认设立“平台协调聊天”入口，由该入口提供经授权的平台任务创建与交接能力，不再设置独立开关。该入口由 Server 管理归属、权限、计划和任务交接，但可选择远程或本机 Worker 上的 Agent Runtime 执行讨论，不要求 Server 直接运行 Agent；使用 Server 所在机器的 Runtime 时也通过该机器上的 Worker。平台级入口不授予全实例数据访问权，仍受当前用户权限限制。普通任务 Session 不因能调用工具而自动获得跨任务派发能力；Worker 独立本地聊天不因节点加入集群而获得平台协调权限。本地任务管理能力与跨集群平台交接权限须区分。

平台协调聊天归属采用方案 A：其专用 Task 直接属于 Team，不强制属于 Project，交接出的普通实施 Task 必须属于 Project。此为对现有 Task 必属 Project 的明确领域扩展；平台协调聊天不再适用前述含 Project/Workspace 的项目内专用任务复用键，其确切复用键另行确认。选定 Worker 与工作目录属于执行绑定，不决定业务归属，也不赋予全项目读取权限。

Runtime 若无法强制约束讨论权限，明确禁止其承担平台协调讨论并说明原因；仍可用于经授权的普通实施任务，不静默降级为仅靠提示词。

普通任务完成策略已确认参考 Paperclip 的可配置审查流程，取代所有任务一律人工审查后才能 done 的旧规则：无审查阶段时，获授权 Agent 可显式提交完成，平台校验权限与阻塞条件后完成；配置 review/approval 阶段时交由相应 Agent 或人工参与者处理，所有要求阶段通过后才完成，要求修改则回到实施。Run 成功不直接等于 Task 完成，专用对话任务不套用普通任务完成规则。审查配置采用项目默认策略与任务级覆盖：新项目默认不强制审查，但仍须显式提交完成；项目管理者可设置 Agent 审查、人工审批或多阶段流程，新任务继承策略，只有具备管理权限的人可调整，执行 Agent 不得自行取消审查。任务开始执行后，项目默认策略变化不得隐式放宽其要求。

专用协调对话生命周期已确认参考 Paperclip：打开页面仅查询，首次发送或上传时自动创建专用 Task；长期复用，处理消息时 active、等待消息时 waiting，不套用普通任务 done/cancelled 或人工审查语义。重新开始上下文时在原 Task 下创建新 Session，保留旧记录；模型切换仍留在当前 Session，不等于重开上下文。

访谈已整体确认：平台协调聊天按 Team + 用户 + Worker + Agent 复用，不包含 Project 或 Model；模型切换不打断当前 Turn，对下一 Turn 生效，保留同一 Session，Runtime 无法支持时明确拒绝，不隐式换会话或降级模型。

平台内置 API 是整体产品方向：Agent 能从项目视角发现获权资源、创建任务、查询任务关联的会话、读取获权执行历史并交接工作。Web、CLI、MCP 和 Runtime 原生工具复用同一应用能力与授权规则；知道 Task ID 不代表可以读取其中全部 Session。具体合同和验收见 [新版前端与项目级 Agent 能力规格](../specs/web-next-project-agent-platform.md)。

用户已整体确认方向，可进入规格落实与实施。本文描述目标而非已交付能力；数据清理必须按明确清单与重建步骤执行，旧前端仍须待全部有效功能迁移及双宿主验收后才能删除。
