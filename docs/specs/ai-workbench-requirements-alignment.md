# AI 集群工作台需求基线与规格校正

状态：已确认方向的需求整理，以及待确认的实施方案。不是已交付声明；没有开放协调入口、授权付费调用或批准数据清理。当前工作只按 spec/ticket 跟踪。

## 1. 用户确认的主线

1. **目标是完成项目**：任务驱动建立在手工创建、继续会话的能力上，以 Project → Task 组织多个 Session，不用管理流程替代实际工作。
2. **看板是主要管理视图，状态驱动任务推进**：参考 Vibe Kanban 的形态呈现任务状态，任务中进入会话、查看变更、验证与成果；手工入口继续可用。任务进入允许开始的状态后，平台按机器范围、授权和容量安排申领或派发，不再要求另一个独立的“加入执行队列”开关。已确认的状态映射见 D1；状态迁移与调度共用授权、幂等及并发控制，不增加额外用户操作。
3. **集群有明确用途**：利用远程机器运行 Agent Runtime 和工具，把任务交给符合条件的空闲机器，提高资源利用率，统一管理执行。
4. **任务声明机器范围**：支持不额外限定机器、指定候选机器集合、指定机器；支持符合范围的机器申领和指定派发。任何方式都不能绕过资源权限。
5. **多用户团队共享使用**：用户和获授权的项目管理 Agent 使用同一套任务管理能力，不维护另一套不可见的 AI 任务账本。
6. **自主推进项目**：Agent 在授权内组织、执行、验证和推进工作；人做关键决策并能随时介入，不要求每个任务先批准计划或每次执行重复确认。
7. **资源不是模型算力**：管理 Agent loop、工具、浏览器、代码执行和构建测试占用的 CPU、内存与执行环境，不建设模型训练/推理调度。
8. **运行形态目标**：loop-in 使用 Worker 本机 Agent Runtime 执行完整 loop；loop-out 使用平台 Runtime 驱动 loop，通过受控接口调用 Worker 执行工具。loop-out 不是任意外部 Agent 的远程工具调用，平台 Runtime 是该形态的一部分，不再另列为无关的来源选择。首条 loop-out 链路已确认采用单 Worker 的完整任务执行，见 D4；平台 Runtime 的部署位置、实现选型与实施优先级尚未确认；使用平台 Runtime 不等于担任项目管理角色。
9. **任务管理可替换**：任务管理须模块化解耦，未来可改用另一套项目管理系统管理任务。内置 Kanban 是当前实现，不是执行调度的硬编码依赖。以稳定 Interface 连接任务管理 Module 与执行 Module，由 Adapter 映射任务标识、版本、状态语义及操作权限；Worker、Runtime、Run/Session 不直接依赖某一看板的数据库或字段。替换不取消 Task 归属、授权、幂等与审计不变量；具体外部系统及同步方式尚未选定，本轮不承诺已有外部集成。

需求来自用户本轮澄清；参考产品只提供实现与交互证据，不能替代需求确认。研究入口：[产品方向记录](../research/ai-cluster-workbench-product-alignment.md)、[三个产品的用户故事核验](../research/kanban-remote-agent-team-story-validation.md)。

## 2. 端到端用户故事

团队接入两台或更多有不同能力的 Worker。成员手工创建任务或授权项目管理 Agent 组织任务，在项目看板说明目标、验收要求、机器范围与分配意图。

平台展示候选 Worker 是否获权、Runtime 是否可用、环境是否就绪、是否还有执行容量。符合条件的机器申领工作，或任务被指定派发；实际运行建立 Task 下的 Session 与不可变 Run 绑定。团队可以同时在其他任务中工作，而不是轮流占用唯一聊天窗口。

用户在看板查看任务进展，在任务内查看排队原因、实际执行机器、会话与结果。Agent 按授权跟进结果和阻塞；用户可补充要求、停止自己有权控制的执行，或处理需要决定的事项。

执行结束后显式提交成果，平台按验收要求与审查策略推进任务。断线不直接表示失败；重连先确认原执行事实，不盲目在另一台机器再跑一次。

### 必须覆盖的变体

- 指定 Worker 忙碌或离线：明确等待/不可用原因，不暗中换机器。
- 两台 Worker 同时申领同一工作：一个执行意图只能有一个有效承接者；重复消息不重复启动。
- 两个成员各自派发任务：授权、执行归属、容量占用与审计不混用。
- 同 Task 多个 Session：研究、实施、验证可以分开；申领互斥不能把整个 Task 永久锁成只能一个 Session，也不能在未定义并行安排时复制执行。
- 同机共享文件：私有 Session 不代表文件隔离，接单前需要确认工作环境和共享风险。
- 用户要求先审计划：批准绑定 revision，修订后重新确认；未要求审批的已授权工作不得被统一审批步骤阻塞。

### 已确认：任务成果审查配置

- 采用“项目默认 + 任务覆盖”，不是全局唯一开关。任务可选沿用项目默认、无需人工审查、需要人工审查；需要时配置多级审查。项目未配置时默认不强制人工审查。
- 只有有权限的用户或管理身份可设置；执行 Agent 不得自行降低要求。开始执行时固定有效审查要求，之后修改项目默认不改变在途任务。
- 不要求人工审查仍需显式提交成果和验收证据，不以 Run 成功直接完成 Task。要求审查的任务通过审查后才完成；依赖其完成的下游在此之前不具备执行资格。
- 计划批准、成果审查、超范围授权是不同的门。确认成果审查配置不等于确认 D6 的全部持续委托规则。

实施责任：[项目管理工具票](../../.scratch/web-next-plan-handoff/issues/01-plan-approval-and-handoff.md)交付配置与同一权限合同，[派发票](../../.scratch/web-next-task-dispatch/issues/01-placement-claim-dispatch.md)消费依赖满足及执行资格；不另增票据。任务依赖图不是现有 `blocked` 状态或仓库 Markdown 票据已经实现的能力。

### 已确认：任务进度记录与同任务接手

Task Progress Record（任务进度记录）是任务持久工作上下文，一个 Task 可有多条，由人或获权 Agent 追加，保留作者、时间和适用的来源 Session/Run。它既记录进展，也可直接供其他 Agent/Session 交接，不另造一套重复的交接报告。

内容与 Agent 工作约定参考 Matt `handoff` skill：让新会话能继续工作，围绕接手目标记录当前进展、未完成事项、关键决定及理由、问题、下一步；已有规格/任务/提交/Diff/证据用路径或获权引用，不复制整份文档；脱敏，必要时给出建议使用的 Skill（建议不是权限授予）。借鉴其内容原则，不沿用临时目录作为产品存储，记录归属 Task。

同一目标尚未完成且需换执行者时，主 Agent 可在授权内为原 Task 安排新的 Session，沿用原审查要求；原任务可保持 in_progress，原会话及记录保留。接手者读取任务要求、相关进度记录及获权成果引用；最新单条不自动代表并行工作的全貌。接手前确认旧执行已停止或安全对账，并准备 Workspace/代码；引用不代表文件已跨机同步。进度记录不自动变更状态、派发执行或授予访问权限；可独立安排的额外工作才另建关联 Task。

实现归项目管理 01（追加/读取、权限、来源、幂等与任务详情）、02 分项 B（真实同任务跨 Session 接手），派发 01 消费明确的接手执行意图；不增加独立票据。

## 3. 保持的不变量

- Session 固定 Task、Worker 与 Agent；新派发只影响新的执行，不迁移已有 Session。
- 任务状态、Run/Invocation 状态、Worker 在线状态、容量和 Journal 新鲜度分别表达。
- Project、Worker、Session 权限独立校验；有机器使用权不等于有其他用户会话、目录或凭据的读取权。
- Run 成功不自动 done；审查按配置，执行者不能自行放宽。
- 不默认跨机同步文件或凭据；Placement 由执行 Worker 确认就绪。
- 用户后续决定协调聊天与普通 Agent 一样运行，不额外限制文件/终端/联网；不以 L1 作用域、隔离证据或人工风险接受作为协调入口前置，隔离另行交付。多用户权限仍不可描述为不互信租户安全隔离；见 [ADR 0008](../adr/0008-coordination-chat-ordinary-runtime-permissions.md)。
- Worker 独立宿主身份与集群身份分离，不自动上传本地记录。

D1 补充合同：机器不可用或无容量时保持 todo 并显示原因；拖动看板和 Agent 操作走同一授权状态机。重复状态事件不重复启动，重新进入 todo 也须核对在途执行，不能复制结果未知的工作。Task 可有多个明确安排的 Session，任务状态不替代 Run/Session 生命周期。Run 成功不自动 done；提交成果后需审查则进入 in_review，无需审查且验收通过可直接 done。进入 blocked/done/cancelled 阻断后续自动派发，对在途进程的停止、恢复按执行控制合同处理。

D6 交互合同：手工看板仍按 D1 操作，不必配置项目管理 Agent 才能执行。项目管理角色不等于某个 Runtime 或 Worker；职责说明和工作模式不替代服务端授权，讨论/计划模式也不能仅靠提示词宣称只读。项目管理 Agent 维护用户同一套 Task、依赖、Session 和成果，不另造隐藏计划账本；依赖解除只是执行资格条件，不自动启动 backlog。超范围操作仍须单独取得授权。参考[委托交互核验](../research/agent-delegation-product-interactions.md)，其中产品事实与本项目选择分开记录。

D6 事件与暂停合同（已确认）：

- 用户交代目标或补充要求时，在授权范围内处理；任务完成、审查通过、依赖解除时检查相关工作是否可继续。
- 机器恢复或容量释放由调度器重新匹配已有 todo，不要求每次唤醒项目管理 Agent，也不由 Agent 轮询机器空闲。
- 首版不做无事定时唤醒的巡检。相关领域事件持久化、去重并有界处理；重启后恢复待处理事件，重新检查当前授权与状态，不重放失效安排。
- 需要人决定、超出权限或达到限制时，只暂停受影响工作，其他独立且获权任务可继续；不得把任意事件或 Agent 自己的状态写入当作无限自唤醒来源。
- 用户暂停项目管理 Agent 后停止新增自动安排，不暗中取消已有在途执行；取消在途执行是单独明确操作。已安排 todo 的调度与管理 Agent 的暂停分开表达，界面须说明影响范围；暂停期间不因恢复事件重新启动管理活动。
- 期限与预算范围（已确认）：首版委托不强制填写期限或金额预算。可随时暂停项目管理 Agent，停止新增安排；取消在途执行单独操作。新增付费服务或扩大授权须确认。能取得的费用如实展示，不能取得的标为未知，不当作零、不承诺严格控费；已授权服务内的执行仍遵守原授权范围。
- 自动截止时间、金额硬上限作为后续独立能力，不属于本次 D5 持续推进验收前置，后续实施另建规格，不在本轮新增票据。任务不设自动失败重试次数，也不以平台猜测的无进展阈值驱动任务状态。本次产品范围确认不授权实际付费、外发或破坏性动作。

D3 补充合同（按最新任务语义修正）：尚未派发时可修改原 Task 的机器范围，不产生虚假的已运行记录。主 Agent 或获权用户核对目标与成果，识别还缺哪些工作：同一目标继续使用原 Task，必要时换 Session 接手；可独立安排的额外工作才创建带目标、验收要求及来源的关联 Task。复制只是可选的录入便利，不是每次异常后必须重建任务；不提供平台自动重试原任务的循环，也不因创建后续任务自动完成原任务。新任务重新检查授权、机器范围、审查要求、代码与 Placement，不复制旧执行权或批准记录。复制操作不自动修改下游依赖；如需调整仍走获权的依赖编辑接口。原执行结果未知时继续先对账，不能以新 Task 身份绕过旧执行安全检查或承诺跨机透明恢复。底层连接恢复、消息幂等重投是对同一执行事实的恢复，不是任务重试。

任务状态权威：人、主 Agent、任务执行 Agent 通过同一任务操作 Interface 表达状态、阻塞及完成，由服务端校验各自权限、CAS、幂等和审查策略。Agent 退出未更新任务时，保留任务状态并独立显示 Run 结果，不从退出码、测试红灯或活动次数猜测任务完成/失败。平台不新增 `failed` Task 状态；技术失败保留在执行记录，任务如何处置由获权主体明确操作。会话内调试与人工退回修改不因此被禁止，也不自动复制任务。

实现者可设计原子预约、幂等、持久化与恢复技术，但不得自行把上表建议变成产品默认。涉及即时停止正在执行工作时，区分阻断后续授权与尽力停止进程，不能承诺撤权能撤销已发生的外部副作用。

### 接手与进度记录的技术约束及待决项

普通派发以 todo 为入口；显式接手可在 in_progress 经同一执行资格 Interface 提交，仍检查依赖、容量、授权和固定审查策略。接手按旧执行身份与代次原子认领，防止不同请求重复接替；旧执行权、排队/迟到消息不能越过交接边界复活，无权处理或事实未知则等待。等容量的接手意图需持久恢复，不要求退回 todo。

进度记录由凭据确定作者，Agent 来源从可信执行绑定解析；人类引用历史执行不伪装为该执行作者。同主体、Task、requestId 重放返回原记录，同键异载荷冲突，重放重验当前权限；并发追加全部保留，分页稳定，无 Run 的合法 Session 来源允许。任务管理 Module 权威保存记录及 Task 冻结审查要求，替换 Adapter/新 Session 接手不丢失或重新计算它们。

本轮复审涉及的边界如下，已确认与待决分别记录：

1. **正文发布范围（已确认）**：追加任务进度记录是向有权读取该 Task 的人和 Agent 显式发布正文；读取正文不额外要求来源 Session 权限，不代表向全实例公开。平台不自动搬入私有会话内容。来源会话、文件与其他引用对象仍独立鉴权，自动生成的引用标题、路径及预览也不得泄漏受限来源。发布入口说明可见范围，统一校验输入和敏感字段，不承诺识别正文里的所有自然语言秘密。
2. **接手决策主体（已确认）**：执行 Agent 负责写入实际进展、剩余工作及困难，不主动发出接手请求或决定接手者。主 Agent 或有权限的人读取任务与进度记录，决定是否接手、由谁接手，再明确提交获权的接手安排；不以执行 Agent 发出请求为前置。首条验收可由用户明确要求主 Agent 评估接手触发；此决定不新增普通记录追加或 Run 退出自动唤醒规则。
3. **接手排队顺序（已确认）**：接手与普通任务统一按本次执行安排入队时间等待；普通任务进入 todo 时入队，主 Agent 或人明确安排接手时为该接手意图入队。接手无特殊优先级，不沿用原 Task 的旧 todo 时间；Task 保持 in_progress 并显示等待接手。仅在机器范围、依赖、权限及容量满足的工作中先入队先安排；旧执行未确认停止时显示等待原执行确认，不启动接手者。持久化入队顺序，重放和重启不重排或重复生成意图。
