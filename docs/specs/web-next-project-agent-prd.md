# Paperclip 风格前端重写与项目级 Agent 协作平台 PRD

状态：`ready-for-agent`。产品方向已经确认，可进入实施；该状态不代表功能已完成或允许立即删除旧前端。

## 问题陈述

用户无法稳定、直观地使用当前前端：打开首页、深链接、切换会话或加载待办可能出现含义不准确的错误；局部修改经常漏掉其他入口、登录状态或宿主差异。仅修补页面和样式不足以消除应用壳、路由、状态及权限判断的历史耦合，也不能靠测试数字证明真实操作可用。

用户希望尽量沿用 Paperclip 成熟的前端和项目管理交互，重新构建一个桌面与手机都可用、完整覆盖现有有效功能的控制台。同时，Wemux 必须明确是位于具体 Agent Runtime 之上的平台：Agent 不应只看到当前聊天文本，还应能在授权范围内理解项目、创建任务、查询任务关联会话、交接计划和报告成果。

现有“任务可选、会话模型固定、任务一律人工完成”的部分产品假设与最新需求冲突。若不统一领域规则，只重写界面，会把同样的问题搬进新目录。另一方面，部署不能再分裂成多套临时实例、账号、数据库和程序版本，使用户无法判断自己正在操作哪套系统。

## 解决方案

以 Paperclip 前端为基础，在独立目录重写，选择性复用其应用壳、设计系统、基础组件、导航和项目管理交互，替换业务层，不直接依赖旧页面。保留 Wemux 的 Server 控制面、Worker 执行节点与多 Runtime 适配边界。

所有 Session 固定归属 Task。普通实施任务属于 Project；平台协调聊天通过 Team 级专用任务承载，负责讨论、研究、计划和授权交接，由选定 Worker 上的 Agent 执行。正式实施进入普通任务，在独立 Session 中执行，不能将原会话换绑。测试和快速试聊也自动提供专用任务，不开放无任务例外。

内置项目级 API 与 Web 共用应用能力，向 Agent 提供受权资源发现、任务管理、关联会话查询、版本化计划和交接能力。通过 Runtime Adapter 按实际能力提供 Skill 指引、CLI/API、MCP 或原生工具入口，而非绑定某一个 Runtime 或强制 MCP。

新旧前端在同一个实例、域名和端口共存：迁移期间根入口暂留旧版，新版通过 `/next/` 使用同一套真实数据和 Worker；旧版不要求持续功能回归，其历史异常不阻断新版。所有现有有效功能迁移并完成 Server、Worker 独立宿主和移动端验收后，才切换默认入口并删除旧前端。历史应用数据允许全部清理，不建设旧会话补绑迁移，但清理必须有明确数据边界、恢复措施和身份重建步骤。

## 用户故事

### 统一体验与完整迁移

1. 作为日常用户，我希望新版沿用 Paperclip 清晰的布局与交互，以便不再学习零散、不一致的操作方式。
2. 作为现有用户，我希望所有现有有效功能都有迁移对应项，以便重写不会悄悄删掉我需要的能力。
3. 作为用户，我希望同一个实例中能区分旧版与新版入口，以便试用新版而不用辨认多套服务和账号。
4. 作为用户，我希望登录后默认进入项目列表，以便从工作的组织上下文开始。
5. 作为项目成员，我希望项目内集中组织任务、会话、工作区、画布及资源，以便不用在全局页面之间反复寻找。
6. 作为手机用户，我希望核心流程和管理功能均能操作，以便不是只能查看缩小的桌面页面。
7. 作为键盘用户，我希望导航、弹窗和表单具有可预测的焦点与快捷操作，以便连续完成工作。
8. 作为用户，我希望保留搜索、命令入口和未保存修改提醒，以便重写不损失现有操作效率。
9. 作为用户，我希望错误明确区分链接不存在、无权限、网络失败和页面异常，以便知道如何恢复，而不是一律看到“链接无效”。
10. 作为用户，我希望深链接、刷新、后退和登录后的返回位置可靠，以便分享和重新打开页面不会丢失目标。
11. 作为局域网用户，我希望 HTTP 环境下随机 ID 和复制操作正确降级，以便按钮不会静默失效或谎报复制成功。

### 账号、项目和资源

12. 作为用户，我希望保留注册、验证、登录、找回、第三方身份绑定和登录会话管理，以便完整管理账号。
13. 作为团队管理者，我希望保留邀请、成员角色和资源授权，以便新版不会改变既有安全边界。
14. 作为项目成员，我希望浏览和管理获权项目、Repository、Workspace 与 Placement，以便知道代码和执行环境实际位于哪里。
15. 作为项目成员，我希望创建环境失败时看到原因并安全重试，以便不用猜测是否已经创建。
16. 作为用户，我希望私有会话仍有独立内容权限，以便加入团队或获得 Task 权限不会暴露我的历史。
17. 作为管理员，我希望管理 Worker 的注册、健康、版本、撤销和诊断，以便统一维护执行资源。
18. 作为用户，我希望选择实际可用的 Agent 与 Model，以便未认证或未验证的候选不会冒充可执行能力。
19. 作为资源管理者，我希望保留 Skill、Preset、Provider 的版本发布和分发状态，以便看到从配置到生效的真实过程。
20. 作为集成管理者，我希望保留连接器、Channel、审批和投递故障处理，以便新界面不丢失外部协作能力。

### Task 与 Session

21. 作为用户，我希望每个 Session 都有明确 Task 归属，以便对话、执行和交付可以追踪。
22. 作为用户，我希望测试或快速试聊时自动提供专用 Task，以便不必为了开始聊天先填写任务表单。
23. 作为用户，我希望不同用户、项目环境或 Agent 的测试不会混入同一任务，以便保持清晰的上下文边界。
24. 作为用户，我希望一个 Task 可以包含多个 Session，以便分别研究、执行或比较模型。
25. 作为用户，我希望 Session 绑定后不被转移到其他 Task，以便历史归属和授权不会悄悄改变。
26. 作为用户，我希望在同一 Session 切换当前 Agent 的模型，以便保留历史而不必另开会话。
27. 作为用户，我希望模型切换不改变已启动 Turn 的模型，以便当前执行可解释且可追溯。
28. 作为用户，我希望不支持模型切换时明确告知原因，以便系统不偷偷换会话或降级模型。
29. 作为用户，我希望保留消息队列、停止、审批、工具事件、用量和历史恢复，以便获得完整对话体验。
30. 作为用户，我希望断线与重启后保留已接受操作并恢复同步，以便重连不重复执行或丢失消息。
31. 作为协作成员，我希望继续使用获权画布、Fork 和会话血缘，以便探索关系而不改变底层任务归属。
32. 作为实施者，我希望在获权任务中使用文件、Diff、终端和成果功能，以便从执行到验收形成闭环。

### 平台协调与计划交接

33. 作为用户，我希望无需先选 Project 就能从 Team 范围开始协调聊天，以便讨论新项目或跨项目工作。
34. 作为用户，我希望可选择获授权 Worker 上的 Agent 作为协调者，以便不要求 Server 本机运行模型 Runtime。
35. 作为用户，我希望相同 Team、用户、Worker 和 Agent 的协调聊天长期复用，以便持续讨论而不堆积无意义任务。
36. 作为用户，我希望打开聊天页只查询、首次发送或上传才创建专用任务，以便浏览行为不产生空任务。
37. 作为用户，我希望协调对话用“处理中”和“等待消息”表达状态，以便不会误认为每次回复都要人工审查。
38. 作为用户，我希望能在原协调任务内新建 Session 重开上下文，以便保留旧记录而不换任务。
39. 作为用户，我希望纯讨论不自动派发实施任务，以便计划研究不会意外触发代码变更。
40. 作为用户，我希望明确授权后直接交接实施任务，以便不为相同授权范围重复确认或配置额外开关。
41. 作为用户，我希望要求先批准计划时看到绑定具体版本的审批记录，以便批准对象不会被后续草稿替换。
42. 作为实施者，我希望交接任务携带相关计划、验收标准和来源授权，以便不必猜测另一个会话中批准了什么。
43. 作为用户，我希望已交接任务固定计划版本，以便协调对话的新草稿不会偷偷改变正在执行的目标。
44. 作为用户，我希望实施任务不会阻塞协调聊天继续交流，以便可以同时讨论后续工作。
45. 作为用户，我希望协调 Agent 不能直接修改代码、安装依赖或部署，以便讨论与实施具有真实权限边界。

### 内置项目级 Agent 能力

46. 作为 Agent，我希望发现当前获授权的项目与资源，以便从项目目标而非孤立消息出发工作。
47. 作为 Agent，我希望查询任务、状态、指派与计划版本，以便理解已有工作并避免重复创建。
48. 作为获授权的协调 Agent，我希望通过内置 API 创建普通任务并保存初始计划，以便可靠交接而不是只在回复里描述任务。
49. 作为 Agent，我希望按 Task 查询实际关联的获权 Session，以便找到相关讨论与执行上下文，而不只看到 Run 列表。
50. 作为 Agent，我希望查询 Session 的获权历史、执行状态和同步新鲜度，以便不把陈旧投影视为最新事实。
51. 作为用户，我希望上述查询不泄漏隐藏会话的标题、内容、数量或关系，以便元数据也受保护。
52. 作为 Agent，我希望写操作具备幂等和版本冲突反馈，以便重试不会重复创建任务或覆盖他人修改。
53. 作为实施 Agent，我希望能提交结果与证据并查询审查进度，以便平台状态反映实际工作。
54. 作为用户，我希望 Agent 不能在调用参数中伪造身份或扩大权限，以便工具入口与 Web 一样可信。
55. 作为平台维护者，我希望 Web、CLI、MCP 和原生工具共用业务规则，以便适配不同 Runtime 不会出现不同版本的任务管理逻辑。
56. 作为 Runtime 使用者，我希望保留 Agent 自身的 todo、计划工具和 Skill，以便平台协作能力不会接管全部内部推理步骤。

### 完成策略与治理

57. 作为项目管理者，我希望新项目默认不强制审查，以便普通工作无需不必要的审批环节。
58. 作为项目管理者，我希望能配置 Agent 审查、人工批准或多阶段流程，以便高风险任务有相应保障。
59. 作为任务管理者，我希望任务继承项目默认策略并可受权覆盖，以便兼顾一致性与特例。
60. 作为用户，我希望 Run 成功不会自动将 Task 标为完成，以便执行终结和交付验收保持区别。
61. 作为审查者，我希望批准、要求修改和后续阶段都有真实推进路径，以便任务不会只挂一句“请审查”。
62. 作为用户，我希望执行 Agent 不能自行移除审查，也不会因项目默认值变化而降低执行中任务的要求，以便授权稳定。

### 多 Runtime、双宿主与交付

63. 作为用户，我希望现有有效 Runtime 通过统一合同使用平台能力，以便不会被绑定到 Pi 专用格式。
64. 作为用户，我希望不能强制限制讨论权限的 Runtime 明确不可担任协调者，以便不以提示词冒充安全控制。
65. 作为 Worker 独立用户，我希望不用 Server 也能管理本地 Task 和 Session，以便保持独立可用。
66. 作为 Worker 独立用户，我希望加入集群不上传或合并本地任务与会话，以便本地身份和数据边界保持不变。
67. 作为操作者，我希望可以清理历史应用数据后按新模型初始化，以便不为可舍弃数据投入复杂迁移。
68. 作为操作者，我希望清理不会删除项目源码、外部仓库或其他应用数据，以便升级不会破坏真实工作成果。
69. 作为操作者，我希望重置时统一处理账号、Worker 注册和传输状态，以便不留下单边清空后的失效身份与重放队列。
70. 作为用户，我希望真实实例、真实 Worker、桌面与手机都通过完整操作验证后才删除旧版，以便切换的是可用产品而非演示。

## 实施决策

### 1. 前端边界与交付

- 新目录独立构建，不导入旧页面、应用壳或路由。经审计的协议和非 UI 行为逻辑可迁入共享模块，旧目录最终可完整删除。
- 固定 Paperclip 参考版本，记录取用范围、改动与 MIT 许可；复用实现而非只模仿外观，但不把其 Company、Agent 等概念机械映射为 Wemux 领域对象。
- 共用设计系统与 Session 交互，通过明确宿主接口区分身份、权限、资源发现和集群生命周期。先打通 Server，再完成 Worker；不能先写死 Server 假设再补大量条件分支。
- 顶层导航组织待办、项目、集群、团队和设置；平台协调聊天有明确入口，项目内提供任务、会话、工作区、画布及资源。现有审批、活动、连接器等有效功能可以重组层级，但不能消失。
- 迁移登记必须精确到用户操作，包含旧入口、现有有效性、目标入口、权限、异常路径与证据。源码存在不等于功能有效；当前已确认的新规则允许替换相冲突的旧行为，其他功能废弃不能自行决定。
- 同实例部署新旧静态前端，处理资源基路径、路由刷新、认证回跳及深链接。权限、会话归属和执行限制必须在后端实施，不能依赖入口路径判断。

### 2. Task、Session 与归属

- Session 必须属于一个 Task，日常不可换绑；Task 不拥有 Workspace 文件生命周期。
- 普通 Task 属于 Project；平台协调专用 Task 直接属于 Team。本地 Task 由 Worker 独立宿主管理，不能伪造为集群资源。
- 项目内专用 Task 按用户、Project、Workspace、Worker、Agent、场景复用；平台协调 Task 按 Team、用户、Worker、Agent 复用。Model 不进入复用键。
- 专用协调任务懒创建且并发幂等，长期复用；对话状态采用 active/waiting，不借用普通任务完成、取消或人工审查语义。新上下文通过原 Task 下新 Session 表达。
- 同 Session 允许切换当前 Agent 的模型；对下一 Turn 生效，保留每次执行的模型快照。队列中的消息在成为实际 Turn 时确定执行模型；切换与启动竞争由权威端排序，不追溯修改已启动 Turn。Runtime 不支持时明确拒绝。
- Fork 保留既有有效能力，但目标 Session 仍须满足 Task 归属与授权；不借 Fork 实现未经确认的跨任务历史搬运。

### 3. 协调、交接与执行权限

- 平台协调聊天可使用任意获权 Worker 上的 Agent。Server 不直接承担 Runtime 执行；部署在同机也走 Worker。
- 不设独立任务创建开关。按模式、用户明确意图、批准记录及资源权限判断是否允许创建与交接普通任务，纯讨论不自动启动实施。
- 必须先审批的计划采用版本绑定记录；修改后不能复用旧批准。交接固定版本及相关内容，普通任务初始计划必须在允许执行前保存完毕。
- 同一获批范围不要求重复批准；超范围变更和工具审批依然适用。普通实施任务不是协调任务的子任务，也不以完成它们作为结束讨论的前提。
- 协调模式允许读取、搜索、分析、保存计划和受权平台交接操作，不允许工作区代码修改、依赖安装、部署或未经授权的外部写操作。Skill 只是指引，限制必须在实际执行边界可靠生效。
- Runtime 无法保证限制时，不支持协调模式；仍可用于获授权的普通实施任务。不得为了使用 CLI 或 API 而放开任意 Shell。

### 4. 完成与审查

- Run 终态与 Task 验收分别记录。无审查要求时，获授权 Agent 可显式提交完成，平台校验权限、版本和阻塞条件后变为 done。
- 新项目默认不强制审查。项目管理者配置默认策略，任务继承并允许有管理权限的人覆盖；执行 Agent 不能自行取消要求。
- 配置审查时，按 Agent、人工或多阶段参与者推进，要求修改返回实施。执行中的任务不随项目默认策略变化而隐式放宽。
- 计划批准、执行授权、结果审查与工具操作审批是不同对象，不用一个“已批准”状态互相替代。

### 5. 内置 API 与适配

- 复用已有项目、任务、会话、执行与授权应用服务，补齐缺少的 Agent 能力入口，不维护单独的“Agent 版任务业务”。
- 最小能力集合包括：可见项目查询、项目资源发现、任务列表和详情、任务创建、任务关联 Session 查询、获权历史查询、计划保存与批准、任务交接与启动、结果提交和审查决定。
- Task 关联 Session 查询基于权威绑定，不以 Run 列表推断全集；返回实际可见 Session 的分页投影，先做权限过滤再计算可见计数。查看 Task 不自动取得私有 Session 内容权限。
- 读取接口具有有界分页、稳定排序和新鲜度信息。写接口使用 requestId 幂等和适用的 CAS；同键不同内容返回冲突，重试保持领域身份。
- Agent 身份由可信调用上下文确定，携带当前操作者、Task、Session、Invocation、操作范围及有效期；不信任 Agent 自报的管理员身份或项目权限。
- Web 使用登录身份及 CSRF 保护；Agent 使用受限能力凭据。有效权限为用户授权、任务范围、工具能力和目标资源权限的交集，凭据不得进入提示词、事件日志或普通输出。
- Runtime Adapter 分别适配进程启动、恢复、标准事件、取消与工具注入；Skill、CLI/API、MCP、原生工具是可替换入口，不要求同时交付所有形式。
- 集群请求仍遵循 Server 控制与 Worker 执行链；独立 Worker 提供本地能力，不因加入集群而自动获得跨项目派发权限。

### 6. 数据重置与部署收敛

- 历史应用数据允许全部清理，不实施旧无 Task 会话补绑迁移。清理前列出 Server、Worker、传输状态、账号与注册身份的影响清单，备份并停止相关执行，再成组重置与初始化。
- 应用数据清理不包含项目源码、外部仓库、Agent 全局认证或其他应用数据；数据库恢复也不能撤销已经发生的文件或外部副作用。
- 沿用统一部署管理入口和一致程序版本，不新增长期预览实例。允许清理历史数据不等于可以提前删除旧前端。

## 测试决策

### 测试边界

主验收边界采用用户已确认的真实链路：浏览器或 Agent 工具入口 → 宿主公开 API → 应用服务 → Worker/Runtime → 持久化结果及可见状态。优先从已有公开入口证明行为，不为每个组件新建独立测试接口。

同一组项目任务用例同时通过 Web 和 Agent 能力入口执行，验证业务规则一致。双宿主通过相同用户场景与各自公开接口验收，不强求本地与集群采用相同身份协议。仅对难以稳定触发的执行竞态、能力约束和恢复边界补充现有 Adapter/传输层测试。

### 好测试的标准

- 断言用户可见结果、权限拒绝、持久化事实和重试行为，不断言组件命名、源码字符串或内部调用次数来替代业务验收。
- 每个缺陷建立能够在修复前失败、修复后通过的回归场景。
- 使用真实迁移后的数据库验证查询，避免桩表结构掩盖 schema 不匹配。
- 浏览器测试等待主要数据与会话内容加载稳定，同时捕获渲染异常、控制台错误、失败请求；“HTTP 200”或“跳转到了地址”不等于页面可用。
- 测试状态区分已实现、已验证、失败、跳过和待外部条件，不能用模拟模型响应替代真实模型认证证明。

### 模块与场景

1. **应用壳与身份**：登录前后首页、深链接、刷新/后退、会话过期、无权限、无效路径、接口失败及恢复，覆盖现有账号流程。
2. **Task/Session 应用服务**：强制任务归属、不可换绑、专用任务并发懒创建、同任务多会话、模型切换与排队/启动竞争、固定执行快照。
3. **项目级 API**：项目资源查询、创建任务、关联 Session 全集、内容与元数据过滤、分页、幂等重试、异体冲突和 CAS。
4. **授权**：多用户、多 Team、多 Project、私有/共享 Session、受限 Worker、过期能力凭据、撤权中的调用和历史订阅；标题、数量、关系和隐藏资源存在性不得侧漏。
5. **计划与交接**：批准具体 revision、草稿变更不影响已交接任务、初始计划保存失败不得启动、交接幂等、范围变化和普通工具审批。
6. **Runtime 与安全**：通过现有有效适配验证平台能力；讨论模式尝试写代码、任意 Shell、外部写操作和私自启动任务时被可靠拒绝，不靠模型自觉遵守。
7. **完成策略**：无审查显式完成、Agent 审查、人工批准、多阶段推进、要求修改、执行者降权无效、策略默认变更不放宽活跃任务。
8. **双宿主**：Server 和独立 Worker 同样提供 Task 绑定对话；本地登录、设置、入退集群、失败重试、断线独立使用与数据不自动共享。
9. **可靠性与完整迁移**：消息流、Journal 新鲜度、重连补传、重复提交、取消竞态、重启、画布/Fork、文件终端、Skill/Preset/Provider 和连接器行为逐项验收。
10. **移动与无障碍**：桌面与手机尺寸下真实操作导航、表单、对话、审批、设置和复杂页面；验证触屏、键盘、焦点、滚动与 HTTP 降级，不仅检查截图。
11. **部署与删除门**：统一版本构建、真实数据重置及身份重建、失败恢复、新旧入口共存、切换与回退；所有有效功能验收通过后才移除旧目录及旧构建依赖。

### 既有测试先例

复用仓库已有的真实 Server/Worker 端到端脚本、共享 Worker Web 浏览器验收、Task/Run/Review API 行为测试、团队资源授权测试、Provider 凭据与进程隔离测试、可靠传输重放测试，以及局域网 HTTP 安全上下文回归模式。新增测试应接入这些入口和约定，而不是再建一套平行的测试系统。

产品验收使用现有真实实例、真实数据与 Worker；单元及故障测试的受控夹具是补充，不构成第二套面向用户的部署，也不代替真实使用验收。可能计费的模型或外部写调用须先取得相应授权。

## 不在范围内

- 新增 Codex 或所有 Paperclip Adapter 的完整接入；此次保证现有有效 Runtime 的迁移与验证，架构保留扩展能力。
- 强制所有 Runtime 使用 MCP，或同时实现每一种工具入口。
- 照搬 Paperclip 全部领域模型、插件市场、运行时调度架构或部署技术栈。
- 整体后端重写；仅实施已确认的新产品规则、必要兼容接口和真实缺陷修复。
- 将 Runtime 内部 todo 全部同步成平台 Task，或以其完成状态直接更新平台 Task。
- Session 日常跨 Task 换绑、跨任务历史搬运、跨 Worker 透明迁移或自动文件同步。
- 旧无 Task 会话的历史兼容迁移；用户已允许清理历史应用数据。
- 为不支持权限限制的 Runtime 以提示词方式伪造安全讨论模式。
- 多 Server 高可用、GPU 编排、原生移动客户端、额外企业连接器及尚未交付的远期功能。
- 无限制自动执行、默认批准付费调用、删除外部源码或其他应用数据。

## 补充说明

本 PRD 综合已确认的前端基础改造、任务化对话、平台协调能力与项目级 Agent API 方向，取代相冲突的历史产品假设；不将未来目标标为当前能力。

Paperclip 参考结论来自本地源码中的项目页面、聊天 Issue 路由与唯一性约束、协调对话指引、执行审查策略、平台 Skill 和多个 Runtime Adapter。指引、类型、目录和实际运行约束必须区分；引用其设计不等于已经验证其所有适配与安全属性。实施取用代码时固定来源版本并保留许可。

交付按四个目标推进：合同与有效功能盘点、Server 主闭环、完整功能及 Worker 双宿主迁移、真实验收与最终切换。内部修复不持续扩张为顶层产品目标。现有未来路线与旧发布票据保留独立状态，不因本次 PRD 发布而自动完成。

最终完成条件：现有有效功能逐项迁移，新增任务与授权规则有行为证据，项目级 API 可被现有有效 Runtime 使用，Server/独立 Worker、桌面/移动端均通过真实验收，统一部署与恢复可执行，之后完成新版默认入口切换及旧前端移除。缺失条件必须保持未完成。
