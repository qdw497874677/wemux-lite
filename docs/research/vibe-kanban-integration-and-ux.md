# Vibe Kanban 调研与 Wemux Lite 结合方案

> 状态：研究与建议，尚未批准实施。本轮仅修改设计文档，不修改产品代码。
> 用户方向修订：会话优先，看板辅助。快速启动自由会话是主路径，任务管理是可选增强；下文的任务执行引导仅适用于从任务发起执行，不得作为所有会话的前置步骤。
> 对照版本：BloopAI/vibe-kanban `7440d3364c5dbc5cd2dee72e76715c1594e39286`（调研时 HEAD）。在线文档可能早于或晚于源码；以下明确区分官方事实、当前系统事实与建议。没有启动 Vibe Kanban 做实机操作，交互判断来自官方截图、文档及源码。

## 1. 结论

借鉴它的**计划与执行分离、任务关联工作区、对话为主的执行工作台、产出审查闭环**，不移植整个平台。

Wemux Lite 的优势仍是统一管理多台 Worker 上已有的 Agent，保留原生 HTTP/SQLite Server、Worker WebSocket 和现有 React/TanStack/Radix/Tailwind；不为模仿页面引入另一套后端或同步中间件。

优先解决的是用户从“进入项目、输入需求”到“看到 Agent 开始回复”的路径，而不是先要求创建任务或增加资源管理层。已有就绪工作区与有效 Agent/模型配置时，选用记忆配置，输入首条消息即可开始；首次缺少环境时才展开最小准备流程。任务看板用于计划、跟踪和审查，需要时再进入。

## 2. 官方事实与可借鉴点

| 已核对事实 | 来源 | 对我们的意义 |
|---|---|---|
| 新版以 Issue 做计划；Issue 可以创建、关联及解除关联 Workspace | [S1][S2] | Task 不等于执行环境；不能改成严格的一任务一工作区 |
| 新建 Issue 时可选择同时创建草稿 Workspace | [S1] | “仅记录任务”与“准备执行”可以在同一入口分流；草稿创建不等于已经运行 |
| Workspace 执行界面分工作区侧栏、对话、上下文面板、详情侧栏；支持显隐、调整尺寸 | [S3][S4] | 对话与辅助信息分主次，而非每个面板都常驻 |
| 移动端源码走独立分支，工作区/聊天/变更/日志/预览/Git 切换，CSS hidden 保留面板状态 | [S4] | 手机不能只是把桌面多栏缩窄；保留草稿和滚动位置，但不必加载全部重型面板 |
| 同一 Workspace 可有多个 Session，共享文件但不共享对话上下文 | [S5] | “新会话”不是“隔离副本”；多 Agent 并行改文件要提示风险 |
| Changes 面板提供文件树、diff、行内评论，评论可带入 Agent 消息 | [S6] | 审查应该有可核对的结果，而不仅是“批准”按钮 |

官方截图 `docs/images/workspaces-interface-overview.png` 的四栏布局信息密度很高，适合宽屏，并不天然比我们的手机体验更好。我们借用交互原则，不照抄四栏、图标密度和英文术语。

另一个边界：Vibe Kanban 的 Issue assignees 文档指团队成员；不是我们的 `Agent Assignment`（Worker/Workspace/Agent/Model 执行意图）。两者不能只按字段名映射。[S1]

## 3. 当前系统事实与缺口

依据 `CONTEXT.md`、`apps/web/src/features/tasks/{board,workspaces,runs,review}.tsx`、`apps/server/src/application/task-service.ts`：

- 已有 Task、工作区绑定、Agent Assignment、Run、Session 和人工 Review；不是从零建设任务引擎。
- 已有统一 `CreationDialog` 和更完整的会话入口。此次建议基于这些改进继续做流程收敛，不重复把“统一弹窗”当成未实现。
- 任务执行仍分散：切到工作区页签、创建/绑定环境、选择 Agent/模型、保存指派，再切运行页填写指令。UI 仍直接展示 Assignment JSON、new/reuse、Run 等内部概念。
- 现有审查可以驱动状态决策，但没有看到完整文件 diff / 行内评论产品闭环。不能把已有“审查按钮”描述为已实现代码审查。
- 一个 Task 同时至多一个活跃 Run；Session 可以跨 Run 复用。
- **Run 当前追踪一次初始消息执行。Run 结束后直接在会话里追加消息，不会自动生成下一次 Run，也不延长原 Run。**这是“任务执行工作台”设计必须面对的语义，不能只换布局就声称实现多轮任务追踪。
- Task 的管理状态与 Run 的运行状态不同；Run succeeded 不自动将 Task 标记 done。

## 4. 模型关系：保留结构，不强行串成单向树

```text
Project 项目
 ├─ Task 任务（目标、验收标准、管理状态）
 │   ├─ 关联 Workspace（可多个；环境可独立存在）
 │   ├─ Assignment（下一次执行的选择，可修改）
 │   └─ Run #1、#2…（每次执行的不可变快照）
 │        ├─ 引用 Session（可复用）
 │        └─ Review（对本次执行的人工决策）
 └─ Workspace（固定 Worker，实际工作目录）
      └─ Session（固定 Workspace / Agent / Model）

Worker 上报 Agent 及其可用模型
          ↓
Assignment = Workspace + Worker + Agent + Model
          ↓ 启动时快照
Run → Session → 消息与工具事件
```

Model 是执行配置，不是 Task 的子任务，也不是 Worker 本身。例：同一个任务第 1 次由节点 A 的 Pi/模型 X 执行，第 2 次改用节点 B 的 Claude/模型 Y。必须在 B 准备环境并新建会话；历史 Run 仍指向 A 的快照，不假装跨节点迁移原会话。

任务可以只用于计划，暂不指定 Agent；项目内也可以有不关联 Task 的自由会话。不强迫所有聊天先建任务。

## 5. 推荐的信息架构

### 5.1 项目导航与执行导航分层

项目级保留：`概览 / 任务 / 工作区 / 会话`。

- **快速会话**：项目主入口和主操作，展示最近会话与输入框；已有环境时直接输入需求并发送，按需修改执行配置。
- **任务**：目标、进度、阻塞和待审查，作为辅助管理入口，不拦截自由会话。
- **工作区**：目录、节点、准备状态、执行环境及占用情况。
- **会话**：跨工作区的可读对话索引，保持前一轮区分，不再变回工作区树。
- 进入具体执行后展示：`返回任务 / 任务标题 / 第 N 次执行 / 会话切换`。独立会话则返回来源工作区或会话列表。

桌面建议：

```text
项目导航（可收起） | 任务标题 / 执行状态 / 查看结果
                  | 对话主区域                  | 结果 / 活动 / 详情
                  |                             | 默认按需打开
                  | 多行输入框 + 本次执行配置摘要
```

- 对话占剩余主要宽度；不在窄 Inspector 里完成长对话。
- 双栏仅在宽度足够时出现，面板支持收起；不足时改全宽页签。不要用固定百分比把聊天压成窄条。
- 常规段落限制适宜阅读行长，代码与工具结果可利用更大宽度；“阅读宽度”和“整个工作台宽度”不要混为一谈。
- 详情不是始终展开的第三、第四列。全局连接诊断仍按需打开。

手机建议：

```text
‹ 返回任务      修复登录问题      ⋯
对话 | 结果 | 详情
当前内容，占满可用区域
输入框（仅对话页）                发送
```

- 项目导航与执行内页签不要同时多层常驻；进入对话优先让出竖向空间。
- 使用动态视口高度、安全区与软键盘适配；切换页签、返回、旋转屏幕后保留草稿和滚动位置。
- 首次进入默认对话；需要处理审批/结果时通过带计数的入口提示，不自动抢焦点。
- 关键按钮触控区域至少 44px，状态不只用颜色表示；无需依赖拖拽或 hover 才能操作。

## 6. 创建交互：统一规则，不做一个万能大表单

所有创建动作继续使用同一创建容器、标题/说明/正文/底部操作结构；桌面弹窗、手机全高表单；默认聚焦、错误就近显示、提交中防重复、关闭脏表单确认一致。联动创建不层叠多个弹窗，在同一容器切换步骤并保留输入。

| 创建对象 | 默认上下文 | 核心字段 | 创建后的去向 |
|---|---|---|---|
| 项目 | 当前团队 | 名称，描述可选 | 项目概览 |
| 任务 | 当前项目 | 标题、描述、验收标准；优先级收在属性行 | 任务详情，或进入开始执行 |
| 工作区 | 当前项目/任务 | 节点、来源、仓库/分支（按来源出现） | 准备状态与可重试错误 |
| 会话 | 当前工作区 | Agent、模型；名称可自动生成 | 完整对话 |

新建任务默认只有一个明确主动作“创建任务”；增加不默认勾选的“创建后开始执行”。后者保存任务后进入执行确认，而不是隐式开跑。若节点离线或初始化失败，任务保留，并停在准确的准备状态。

看板列头可增加新建入口并预填合法初始状态，但服务端必须允许该状态；不要为了视觉一致允许用户直接创建一个绕过验收的“已完成”任务。

### 开始执行面板

把现有跨页签步骤组合成一次引导：

1. **执行环境**：选择已关联、已就绪的工作区；没有则就地创建。选定工作区后 Worker 已确定，不再让用户重复选择相互冲突的节点。
2. **执行配置**：展示这个 Worker 实际可用的 Agent 与模型；离线、未安装、未认证都说明原因，不伪造可用模型。
3. **确认指令**：由任务目标与验收标准生成可编辑初稿，展示“新对话 / 继续已有对话”而不是 new/reuse。
4. **开始执行**：确认后进入完整执行工作台，保留返回原任务的路径。

这只是统一用户入口，不能把各个 HTTP 请求假装成跨节点原子事务。Task、Workspace 创建、Assignment 保存、Run 启动逐步持久化；部分失败应从已成功步骤继续。启动请求结果未知时用原 requestId 核对，不重新生成请求造成重复执行。

## 7. 任务管理闭环与多轮执行

```text
待规划 → 待开始 → 开始执行 → 查看对话与结果 → 请求人工审查
                                         ├─ 通过 → 已完成
                                         └─ 要求修改 → 已阻塞 → 准备修改 → 下一次执行
```

此图表示用户流程，不表示 Run 完成自动驱动 Task 流转。所有状态变更必须经现有 capabilities 与版本检查；启动是否需要先迁移到进行中，应明确呈现并处理两步失败。

任务卡片展示两个维度：
- 管理阶段：如“进行中”或“待审查”。
- 最新执行摘要：如“正在执行 / 执行结束 / 执行失败 / 等待审批”，附节点/Agent（按权限可见）。

主动作随状态变化：未准备时“准备执行”，就绪时“开始执行”，活跃时“查看执行”，结束时“查看结果”，审查中“处理审查”。不可用时给明确原因与修复入口，不仅是灰按钮。可见会话标题、事件、结果仍受 Session 权限约束。

### 必须先定清的修订执行语义

短期推荐保持 Run 现有边界：
- “继续此任务执行”显式发起下一次 Run，可复用满足归属/空闲/Agent/模型条件的 Session。
- 审查意见进入下次执行指令草稿，经确认后启动，不静默发送。
- 普通会话发送保留为自由对话，并明确不计入上一次 Run。
- 不把 Run=一次初始消息悄悄改成 Run=无限期多轮协作；后者需要新的结束、取消、恢复、审查失效规则。

审查时还要处理文件变化：同一工作区的其他 Session 或自由消息可能改变文件。未来 diff 审查必须引用明确的基线与结果版本，不能把“当前目录的 diff”永远当成旧 Run 的产物。最小版本至少展示版本/采集时间和工作区共享提示；无法精确归因时写明这是工作区变更，不是该 Run 独占产出。

## 8. 保留轻量架构的能力接入

| 层 | 保留与建议 |
|---|---|
| Server | 身份/权限、Task/Run/Review 管理状态、幂等与事件投影；不操作远端目录 |
| Worker | Agent 探测与执行、Session Journal、环境准备；后续在此增加受限 Git 状态/diff 采集 |
| Web | 工作流组合、对话/结果展示、人工决策；不能自己推断执行成功或绕过 capabilities |

新增结果能力优先“只读”：Worker 采集 git status、基线、文件变更和测试摘要，经现有认证通道提供。限制文件路径、大小和二进制输出，避免泄漏凭据。先不实现任意远程终端或内嵌 dev server；它们涉及进程寿命、端口转发、认证与浏览器隔离，明显超出一轮 UI 优化。

不会为了追随 Vibe Kanban 引入其整套远程服务或同步基础设施。独立源码复核确认，其 Remote Host 是承载仓库、Agent 与进程的完整本地 backend，经 relay 接收远程浏览器 HTTP/WS 隧道；不是我们的中央 Server 通过 Worker WS 管理轻量节点。远程 Issue/协作数据使用 Postgres，本机执行数据使用 SQLite；没有确证存在与我们等价的 Agent/模型清单上报协议。依据：固定版本 `crates/server/src/runtime/relay_registration.rs`。

另一个不宜照搬的差异是自动流转：Vibe Kanban 首个关联 Workspace 可推动 Issue 进入 In progress，PR 打开可进入 In review，满足合并条件可进入 Done；其 ExecutionProcess Completed 本身不等于任务完成。我们的完成条件仍按现有人工 Review 与 capabilities 执行，不因借鉴界面就引入 PR 合并自动完成规则。依据：固定版本 `crates/remote/src/db/issues.rs:520–617`。

## 9. 分阶段落地及验收

### 第一阶段：启动流程与任务化文案
- 任务创建后进入详情或“开始执行”；整合绑定、指派、指令确认入口。
- JSON、requestId、Journal 序号放诊断区，主界面用中文摘要。
- 任务主动作、两维状态和完整对话跳转保持一致。
- 验收：已有就绪环境从任务详情到启动不跨多个 Tab；离线、未认证、初始化失败、启动超时不丢任务与草稿，不重复 Run。

### 第二阶段：执行工作台
- 完整对话为主，桌面辅助面板按需出现；手机对话/结果/详情切换。
- 下一次任务执行入口与自由对话有明确区分；返回任务保持看板筛选与滚动。
- 验收：390/768/1440px，长代码、长中文、软键盘、切换 Session、Worker 重连；草稿和历史不丢，无重复发送。

### 第三阶段：可验证结果与审查
- Worker 只读变更摘要与基线，Web 结果面板；非 Git 工作区展示可用的结果与测试证据。
- 审查意见进入下一次执行草稿；Review 决策仍走 CAS/权限。
- 验收：结果绑定明确基线；工作区变化不冒充旧 Run 结果；无权限不可见；通过才完成。

### 后续再评估
- 行内 diff 评论、Git worktree 优化隔离、PR 关联、命令面板。
- 暂缓多仓库 IDE、任意远程终端、内嵌预览、复杂多人实时同步、自动完成任务、多活跃 Run 调度。

**按用户修订后的优先级：先做快速会话与完整对话工作台，再收敛任务执行流程，最后补结果审查。**

### 会话优先的快速路径（优先于上述任务引导）

- 项目页主操作为“新对话”，最近会话可直接继续；不要求先建 Task、Assignment 或 Run。
- 就绪环境存在时，输入框旁用一行摘要展示 `工作区 · 节点 · Agent · 模型`，点击才展开配置。记忆最近一次成功使用且当前仍可访问、可用的项目配置；仅存在唯一有效选项时可自动选用。多项且没有历史偏好时，用同一面板做最小选择，不任意选择节点或目录。
- 用户第一次发送时创建 Session，再将首条消息交给现有发送链路；只有确认提交成功才清除草稿。Session 创建成功但发送失败时留在该 Session 重试；结果未知时核对原请求，不盲目重建会话或重复发送。
- 首次没有工作区时，在当前入口补充节点与目录/仓库；同一面板完成准备和 Agent/模型选择。准备失败保留输入，成功后继续原会话启动意图。
- 无效配置、离线节点、未认证 Agent 必须显示原因；不能为追求速度静默切换工作目录、Worker、Agent 或模型。已存在会话配置保持不变，切换执行身份使用新会话。
- 会话内“转为任务”是可选后续能力：预填标题、目标和验收标准，由用户确认。现有自由聊天不追溯伪装成 Run，也不冒充已有任务关联；若需要关联既有 Session，先核对并实现明确的归属与权限合同。
- 从 Task 发起执行仍保留 Run/Review 追踪，但复用快速入口，带入目标与已绑定配置，减少重复填写。

验收核心：已有就绪环境时，从项目进入到首条消息提交无需先穿过任务创建、工作区管理和指派页；配置摘要始终可见、草稿不丢、失败不重复建会话或发送。
